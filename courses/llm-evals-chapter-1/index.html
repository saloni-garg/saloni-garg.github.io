Why Your App Is Already Broken
(And Demos Won't Tell You)

LLM Evals From Zero: build an eval suite that blocks bad releases. This chapter sets up the problem the whole course solves: a change that looks better in a demo and is measurably worse in production.

Slide 02 · The core problem

Why "looks good" is not a metric

A metric is a number you can compare across two versions of a system and act on. A vibe check produces none of the properties a release decision needs.

Property a release decision needsVibe checkMeasured evaluation
ReproducibleDifferent reviewer, different verdict. Mood, order, and recency all leak in.Same dataset, same scorers, same result. Anyone can rerun it.
ComparableNo baseline. "Better than last week" is unrecorded memory.Candidate is diffed against a saved baseline run, per category.
CoverageWhoever demos picks the examples, so the sample is biased by construction.Dataset is stratified on purpose: easy, hard, adversarial, out of scope.
ActionableOutput is an opinion. Nothing in CI can consume an opinion.Output is a score against a threshold. A gate can merge or block on it.
Attributable"Quality feels off" names no component and no fix.Failures cluster by cause: retrieval, generation, refusal, citation.

Engineering question: what exactly am I measuring, and could a script act on the answer?

Slide 04 · The change

A prompt change that appears to improve quality

Prompt v13 asks for warmer, more complete answers. In the demo the answers read better: fuller, friendlier, more confident. Nothing about the demo tells you what it cost.

prompts/support_v12.txt → support_v13.txt
# system prompt diff - Answer using only the provided context. - If the context is silent, say you do not know. - Cite the source for every claim. + Be a warm, helpful support expert. + Give complete answers. Fill small gaps + with your general product knowledge. + Keep citations where they fit naturally.

What the change really does

  • Removes the grounding constraint. "Fill small gaps" is a license to hallucinate.
  • Weakens refusal. A warm, complete answer is the opposite of "I do not know."
  • Makes citations optional. "Where they fit" means unverifiable claims ship.
  • Improves surface quality. Longer, warmer text reads better in a spot check, which is exactly why the demo passes.

Engineering question: which behavior did this diff trade away, and who measured it?

Slide 07 · Failure analysis

Failure taxonomy: name it to measure it

A single accuracy number hides everything. Split failures by cause and each one gets its own scorer, its own owner, and its own fix.

Hallucination

Answer asserts facts absent from the retrieved context.

Signal: claims with no supporting chunk.

Scorer: faithfulness judge plus citation check.

Retrieval failure

The right chunk never reaches the model, so no prompt can save the answer.

Signal: expected source missing from top-k.

Scorer: recall@k, deterministic.

Refusal error

Answers what it should refuse, or refuses what it could answer.

Signal: behavior mismatch on should-refuse set.

Scorer: confusion matrix, next visual.

Citation error

Citation present but wrong, stale, or not supporting the claim.

Signal: cited chunk does not entail the sentence.

Scorer: citation accuracy check.

SLIDE 07 / 20PACE 6:00
Slide 08 · Sampling bias

Why demos systematically miss these failures

Demo failure is not bad luck. Four structural biases guarantee the demo sample looks nothing like production traffic.

1 · Selection bias

The presenter picks examples the system is known to handle. The sample is filtered by the outcome before it is shown.

2 · Distribution bias

Demo queries are short, clean, and in scope. Production adds typos, ambiguity, multi-part asks, and out-of-scope requests, which is where refusals and retrieval break.

3 · Sample size

Five examples cannot reveal a failure mode that fires on 5 to 10 percent of traffic. Rare per query, certain per day at production volume.

4 · No baseline, no memory

A demo compares the new version against a feeling about the old one. Regressions on categories nobody re-tests are invisible by definition.

Demo sampleProduction distribution
Query sourceChosen by the teamReal user traffic, logged
Should-refuse casesAlmost never shownA fixed slice of the golden set
Verdict"Looked good live"Scored, diffed, gated

Slide 09 · Definition

What is an evaluation? A formal definition

An evaluation is a repeatable procedure that runs a system over a fixed dataset, scores the outputs against defined criteria, and compares the result to a decision rule.

Eval = D dataset × S system under test × M scorers → report → G gate

D · Dataset

Fixed, versioned inputs with expected behavior per item.

S · System

The exact candidate: model, prompt, retriever, config, all pinned.

M · Scorers

Deterministic checks, reference scoring, and judges, per category.

G · Gate

Pre-agreed thresholds that turn a report into a merge or block call.

evals/run_eval.py · the whole idea in 10 lines
def run_eval(dataset, system, scorers, baseline): results = [] for case in dataset: # fixed, versioned inputs output = system.run(case.query) # candidate, fully pinned scores = {s.name: s.score(case, output) for s in scorers} # per category, never one number results.append({"id": case.id, **scores}) report = diff(aggregate(results), baseline) return gate(report) # PASS or BLOCK, nothing vaguer

Slide 10 · Two loops

Offline vs. online evaluation

Offline evals answer "should this ship?" before release. Online evals answer "is it still true?" after release. You need both; they catch different things.

DimensionOffline evaluationOnline evaluation
WhenPre-release, on every candidate changePost-release, continuously on live traffic
DataGolden dataset: fixed, labeled, versionedSampled production traffic, often weakly labeled
Ground truthExpected answers, sources, and refusal labelsUser signals, judge scores, human spot review
Decision it drivesMerge or block the releaseRollback, canary promotion, dataset updates
Blind spotCannot see queries nobody anticipatedCannot run a controlled A/B against a baseline build
Failure it catchesThe v13 regression on slide 6Drift: new products, new phrasing, stale docs

The loop between them: every real failure found online becomes a permanent case in the offline golden set. The dataset is a growing memory of everything production has taught you.

SLIDE 10 / 20PACE 9:00
Slide 11 · Boundary 1 of 3

Evals vs. unit tests

Unit tests verify code behaves as specified. Evals measure how a probabilistic system behaves across a distribution. Related discipline, different object.

DimensionUnit testsEvaluations
Unit under testA function or componentThe whole system: prompt, retrieval, model, config
OutputDeterministic: same input, same outputProbabilistic: same input, a distribution of outputs
OracleExact expected valueCriteria, references, rubrics, and judges
Pass conditionBinary: pass or fail per testAggregate scores vs. thresholds, plus per-category gates
FlakinessA bug: tests must never flakeManaged: fixed seeds where possible, noise bands, rerun rules
Cost per runMilliseconds, freeReal API calls: budget it, cache it, subset it in CI

Rule of thumb: if the expected output can be written exactly, write a unit test. If quality is a matter of degree across many inputs, write an eval. Most LLM systems need deterministic checks inside the eval suite too, which is Chapter 4 of this course.

SLIDE 11 / 20PACE 10:00
Slide 12 · Boundary 2 of 3

Evals vs. observability

Observability tells you what the system did in production. Evaluation tells you whether what it did was good. Traces without scores are surveillance, not measurement.

DimensionObservabilityEvaluation
QuestionWhat happened? Latency, tokens, errors, tracesWas the output correct, grounded, and safe?
WhenLive traffic, after releaseBefore release on datasets, and sampled live
DataLogs, spans, metrics from real requestsInputs paired with expected behavior and scores
ComparisonAgainst time: yesterday vs. todayAgainst a baseline build on identical inputs
ActionAlert, debug, roll backMerge or block, promote or hold a canary

Worked example

Observability shows latency up and zero errors after v13 ships. Everything looks healthy. Only the eval report shows faithfulness and refusal correctness down, because wrong answers return HTTP 200.

How they compose

Traces feed evals: sampled production traces become scored cases and, once labeled, golden dataset entries. Observability is the supply chain; evaluation is the judgment.

SLIDE 12 / 20PACE 11:00
Slide 13 · Boundary 3 of 3

Evals vs. guardrails

Guardrails intervene on a single live request. Evals decide whether the system as a whole is fit to ship. One is a runtime control; the other is a release control.

DimensionGuardrailsEvaluations
ScopeOne request or response at a timeThe full system across a dataset
TimingInline, in the request path, adds latencyOffline in CI, plus sampled checks online
ActionBlock, redact, rewrite, or refuse that responseBlock or approve the release itself
What it cannot doDetect a slow quality regression across thousands of allowed responsesStop a single harmful response in real time
ExamplePII filter on outputs; a refusal classifier in the pathRefusal correctness scored over the should-refuse set before merge

And guardrails themselves need evals. A guardrail is a model or ruleset with its own false positives and false negatives. You measure those with the same machinery: a labeled dataset, a confusion matrix, and thresholds, exactly like slide 7.

What each stage guarantees

  • Dataset: the questions never change mid-comparison. Version it like code.
  • Model: one pinned candidate per run. No silent provider drift inside a run.
  • Scorers: cheap deterministic checks first, judge only where judgment is needed.
  • Report: a diff, not a score. Baseline vs. candidate, per category, with failing case IDs.
  • Gate: thresholds agreed before the run, so the decision is not negotiated after it.

Slide 16 · Deployment pipeline

Where evaluation fits into CI/CD

Two speeds keep the gate affordable: a fixed subset on every PR for a fast signal, and the full suite nightly for the complete picture.

PR Opened
Lint and unit tests first
→
Eval Subset
Fixed slice of the golden set, runs in minutes
→
Report Comment
Baseline vs. candidate diff posted on the PR
→
Gate
Block on critical regression, warn on cost drift
→
Merge + Nightly
Full suite nightly, canary before full rollout
.github/workflows/evals.yml
on: [pull_request] jobs: eval-gate: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - run: pip install -r requirements.txt - run: python -m evals.run --subset pr - run: python -m evals.report --post-pr-comment - run: python -m evals.gate --baseline main # exits non-zero on a gated regression

Gate policy used in this course

  • Block on any critical category regression: refusal, faithfulness, safety.
  • Block on an overall drop beyond the suite noise band.
  • Warn, do not block, on cost and latency drift. Page a human, not the pipeline.
  • When the gate fires, read the failures, not the score. The report links every failing case.

Engineering question: how do I know whether to block a release? The gate policy answers it before the PR exists.

Slide 17 · The build

What this course will build

One project, built in order: a versioned eval suite in a repo that runs on every PR, compares candidates against a baseline, and fails the build when quality regresses.

The artifacts you will own

  1. Golden dataset: stratified JSONL with expected answers, sources, and refusal labels
  2. Scorer library: deterministic checks, retrieval metrics, citation checks
  3. Calibrated LLM judge: a rubric validated against your own hand labels
  4. Eval report: baseline vs. candidate diff, per category, with failing cases
  5. CI gate: GitHub Actions workflow that merges or blocks on the report

The skills behind the artifacts

  • Failure analysis: cluster failures into causes before touching a prompt
  • Judge calibration: measure judge vs. human agreement and fix the rubric, not the labels
  • Threshold setting: separate real regressions from run to run noise
  • Suite maintenance: fold production failures back into the dataset, re-baseline deliberately

Tooling stays boring on purpose: plain Python, pytest, JSONL, GitHub Actions. Tracing and dashboards appear as an optional layer, never as the core idea.

Slide 18 · Repository preview

Repository structure: one suite, one home

Everything the pipeline needs lives in the repo and is versioned with the code it judges: dataset, scorers, judge prompts, baselines, and the workflow.

llm-evals-from-zero/
llm-evals-from-zero/ ├── app/ │ ├── rag.py # the support RAG system │ └── prompts/ # v12, v13, ... pinned ├── evals/ │ ├── run_eval.py # dataset x system x scorers │ ├── scorers.py # deterministic + retrieval │ ├── judge.py # rubric + judge prompts │ ├── report.py # baseline diff, PR comment │ └── gate.py # thresholds, exit codes ├── data/ │ ├── golden_v1.jsonl # the golden dataset │ └── baselines/ # saved reference runs ├── tests/ # unit tests for scorers └── .github/workflows/ └── evals.yml # the CI gate

Versioning rules that keep it honest

  • Dataset changes are PRs too. Editing the golden set to make a failing build pass is the one unforgivable move.
  • Judge prompts are code. Changing the judge changes the measurement, so judge changes re-baseline the suite.
  • Baselines are saved runs, not remembered numbers. Every report names the baseline it diffed against.
  • Broken variants ship in the repo on purpose, so each chapter can break the system and watch the suite catch it.

Slide 20 · Takeaways

Key takeaways, and what comes next

Five things to keep

  1. "Looks good" is not a metric. If a script cannot act on it, it cannot gate a release.
  2. Demos are biased samples. Small, cherry picked, and missing exactly the cases that fail in production.
  3. An eval is dataset, system, scorers, report, gate. Drop any one and you have an opinion again.
  4. Measure by category. Faithfulness, retrieval, refusal, and citations fail for different reasons and need different fixes.
  5. The gate is the point. Thresholds agreed in advance turn measurement into a deployment decision.
