01 · The lie

Peak tokens/sec is not capacity.

Peak is measured closed-loop, warm cache, one prompt shape, no arrivals. Production is open-loop, mixed shapes, and an SLO. The gap between them is where outages live.

What demos report
12,400 tok/s

Max throughput, concurrency cranked until latency is unbounded. No TTFT bound. No tenant mix. No burst.

What production keeps
Goodput

Max request rate where every SLO still holds. Often 35–60% of peak on a mixed trace. That — not peak — is what you can sell.

Rule for this course: if a number has no arrival process, no SLO, and no cache state attached, it is marketing. We discard it.

03 · Two tenants, one fleet

Same GPUs. Opposite physics.

Tenant A — Interactive chat
350 in · ~220 out
  • Latency-sensitive: user is staring at the first token
  • Short prefill, decode-dominated lifetime
  • Dies on queueing + long-prefill blocking
Tenant B — Document QA
18K in · ~400 out
  • Throughput-sensitive: answer in tens of seconds is fine
  • Long prefill, huge KV footprint per request
  • Dies on KV exhaustion + prefill stalls
Every hard problem in this course is an interaction effect: Tenant B's 18K prefill and KV hold time, paid for with Tenant A's latency.
04 · The SLO contract

Stated up front. Never moved.

Chat · TTFT p95
≤ 800 ms

Arrival → first token streamed. Includes queue wait. Not “prefill time” in isolation.

Chat · TPOT p95
≤ 50 ms

Time per output token after the first. ~20 tok/s floor per stream feels responsive.

Doc QA · Completion p99
≤ 30 s

Arrival → last token for the 18K / 400 workload. The tail, not the mean.

Why percentiles? Means hide the exact requests that page you. A p95 TTFT breach on 5% of chat traffic at 40 req/s is 2 angry users per second.

05 · The dashboard that matters

Four numbers define a deployment.

1 · TTFT

Time to first token

Queue + prefill + first decode. The responsiveness number.

2 · TPOT / ITL

Per-token time

Decode step time. The streaming smoothness number.

3 · Goodput

Throughput at SLO

Useful work only — requests inside SLO count.

4 · KV headroom

Cache left

Free KV bytes / blocks. The capacity cliff number.

GPU utilisation is not on this list. A GPU at 98% can be doing the wrong work — recomputing evicted prefixes, decoding requests already past SLO, or thrashing KV.

06 · Anatomy of a request

Five stages. Each can queue.

1 · ArriveTimestamped by the harness. Poisson process, not a for-loop.
→
2 · QueueWaits for scheduler admission + KV blocks. Unbounded if you let it be.
→
3 · PrefillAll prompt tokens in parallel. Compute-bound. Sets TTFT.
→
4 · DecodeOne token per step, KV grows by 1 token/step. Bandwidth-bound.
→
5 · Stream / DoneTokens flushed to client. KV freed — or held by prefix cache.
Continuous batching: stages overlap across requests — a request decodes while another prefills in the same engine step budget.

*Illustrative shape from the lifecycle model, labelled as such in the course — measured values replace these in Chapter 5 on the frozen trace. Shape is the lesson: at B=1 decode dominates and queue is ~0; at B=64 per-request latency rises while fleet throughput rises ~an order of magnitude.

Batching is not free speed. It is a latency-for-throughput trade you make explicitly, per tenant — or accidentally, in production.

08 · Two regimes

Prefill computes. Decode waits on memory.

Prefill · Compute-bound

FLOPs ≈ 2 · N · P
N = 70e9 params · P = prompt tokens

18K prompt ≈ 2.52 PFLOPs of matmul. Parallel across tokens → high arithmetic intensity → hits Tensor Core roof (989 TFLOPS/GPU BF16 dense).

Decode · Bandwidth-bound

Bytes/step ≈ weights + KV read
BF16 weights = 140 GB

At B=1 you re-read ~140 GB to emit one token. Floor: 140 GB ÷ (4 × 3.35 TB/s) ≈ 10.4 ms/token before KV, overhead, and TP all-reduce. Batching amortises the weight read — that is the whole game.

Roofline crossover: intensity = FLOPs / byte. Prefill (P large) → right of ridge. Decode (B small) → left of ridge. Same GPU, opposite bottlenecks.
09 · Queueing collapse

At 85% utilisation, waiting explodes.

Kingman intuition
Wq ∝ ρ / (1 − ρ) · variability · service time

ρ = arrival rate / service rate. ρ: 0.5 → 0.9 multiplies the ρ/(1−ρ) term from 1× to 9×. Variance in service time — an 18K prefill next to a 350-token prefill — multiplies it again.

What this means on the trace
  • Mean utilisation can look “safe” while p95 TTFT is already breached
  • Bursts at 3× mean rate do not need to be long — the queue they build drains at (service − arrival) speed
  • Admission control + tenant isolation beat “add GPUs” as the first fix
10 · Number 1 in detail

TTFT = queue + prefill + everything you forgot.

TTFT = Wqueue + Ttokenise + Tprefill(P, chunk, batch) + Tfirst-decode + Tnetwork

Chat: P=350

Prefill is small (~18 ms class at scale). TTFT is usually queue-dominated under load. Optimising the kernel misses the point.

Doc QA: P=18K

Prefill is the term. Chunked prefill (Ch 4) slices it so it stops head-of-line blocking chat.

Prefix cache hit

Shared system prompt cached → effective P collapses. TTFT measured cold vs warm must never be averaged (Ch 5 rule).

11 · Number 2 in detail

TPOT: the step time every token pays.

Per decode step

read weights (amortised ÷ B)
+ read KV for all B sequences
+ attention + MLP kernels
+ TP all-reduce (× 80 layers, TP>1)
+ scheduler + sampling

The trade in one line

Raise B → weight cost per token falls, KV read + step latency rise. TPOT p95 ≤ 50 ms caps how far you can push B for chat — even while doc QA would happily go further.

ITL vs TPOT: ITL is the observed gap between streamed tokens (includes jitter); TPOT is the mean step budget. We report both; SLO is on TPOT p95 + ITL p99 in the harness.

12 · Number 3 in detail

Goodput: find the knee, then back off.

  • Sweep offered load on the frozen trace, per engine, identical method
  • Goodput = highest load where chat TTFT p95, TPOT p95, and doc p99 all hold for the full window
  • Operate at ~70–80% of the knee — the burst profile needs the headroom (next slide)
  • Ch 5 produces this curve for real; Ch 6–8 re-draw it per precision / parallelism / speculation
13 · Number 4 in detail

KV cache is your real capacity limit.

bytes/token = layers × KV heads × head_dim × 2 (K+V) × dtype bytes
= 80 × 8 × 128 × 2 × 2 = 327,680 B ≈ 0.33 MB / token (BF16, GQA-8)
One doc QA request
~5.9 GB

18K tokens × 0.33 MB held for its whole lifetime — prefill through last decode.

Fleet KV budget*
~165 GB

320 GB HBM − 140 GB BF16 weights − activations / workspace / fragmentation reserve.

Ceiling it implies
~28

Concurrent 18K sessions, theoretical max — before chat KV, prefix cache, and fragmentation. Ch 3 does this math properly.

*Worked estimate for teaching the method; the capacity calculator in Chapter 3 replaces it with engine-reported block budgets. Note what GQA bought: with 64 KV heads this would be 2.5 MB/token and the doc tenant would not fit at all.

14 · Traffic shape

Poisson in. Bursts included.

Open-loop replay (ours)
  • Arrivals follow the trace timestamps regardless of completions — queues are allowed to form and be measured
  • Inter-arrival: Poisson (exponential gaps) per tenant, seeded and versioned
  • Two profiles: steady mean rate, and burst at 3× mean
Closed-loop blasting (not ours)
  • N clients, next request only after the previous returns
  • Self-throttles exactly when the server struggles — hides collapse, flatters throughput
  • Fine for kernel microbenchmarks. Disqualifying for capacity claims
If your load generator cannot produce a queue, it cannot measure the thing that will page you.
15 · Method, before results

The harness is the course.

Replay

Fixed trace file, seeded generator, per-tenant histograms — never one blended p95.

Cache state

Cold vs warm prefix cache reported separately. Warm-up window excluded, stated.

Observe

Prometheus: queue depth, KV %, prefix hit rate, goodput. Nsight for kernel timelines when numbers disagree.

Cost

Every throughput result lands in the workbook as $ / 1M tokens per tenant. Ch 9 closes it.

Built properly in Chapter 5. Chapter 1's job is narrower: freeze what it will measure, so no later chapter can move the goalposts.
