Chapter 3 · Technical Tutorial

The KV Cache Is Your
Real Capacity Limit.

Weights are a fixed tax. KV cache is the variable that eats the rest — one token at a time, per layer, per request, for the request's whole life. This chapter derives its cost from the model config and turns it into exact concurrency ceilings for the frozen workload.

The derivation

Bytes per token from first principles: 80 × 8 × 128 × 2 × 2 = 327,680 B. Every capacity number in the course is this number, multiplied.

The ceilings

Why the fleet fits ~685 chat sequences but only ~21 doc QA sessions — and why tensor parallelism does not multiply that.

Deliverable

A capacity calculator: model config in, max concurrency per context length out. Live on slide 19 — try it here, ship it in the repo.

Workload unchanged: Llama-3.1-70B-Instruct, 4 × H100 80GB, TP=4, chat (350 in / 220 out) and doc QA (18K in / 400 out), SLOs frozen in Chapter 1. Use ← → or Space to move.

01 · The thesis

Weights are fixed. KV is rent, paid per token.

Weights · paid once
140 GB

70B params × 2 B (BF16), loaded at startup, identical whether you serve 1 request or 1,000. Sharded over TP=4: 35 GB per GPU. It never grows, never shrinks, and it is not what pages you at 3 a.m.

KV cache · paid per token, per request
0.33 MB / token

Every prompt token writes KV at prefill. Every decode step appends one more token of KV. It is held from admission to the last generated token — so cost is context length × lifetime, not just length.

The capacity question is never “does the model fit?” It fits on day one. The question is: after weights, how many tokens of conversation can the remaining memory hold — and that is a number you can compute on paper before you rent a single GPU.
02 · Bytes per token, derived

Five factors. No free parameters.

1
Per layer, per token: KV heads × head_dim = 8 × 128 = 1,024 elements for K, and the same again for V → 2,048 elements.
2
All layers: 2,048 × 80 layers = 163,840 elements per token, fleet-wide.
3
At BF16: 163,840 × 2 B = 327,680 B = 320 KiB ≈ 0.33 MB per token.
4
General form (hybrid / sliding-window models): sum over layers — each layer contributes its own kv_headsl × head_diml. A sliding-window layer only holds its window, so its long-context cost caps out.
bytes/token = L × Hkv × Dhead × 2(K+V) × dtype_bytes

= 80 × 8 × 128 × 2 × 2
= 327,680 B / token (BF16)
= 163,840 B / token (FP8 KV)

Read the config, not the marketing: everything on the right side sits in config.json — num_hidden_layers, num_key_value_heads, hidden_size ÷ num_attention_heads. If a capacity estimate cannot be traced back to these fields, it is a guess.

03 · Why GQA is a capacity feature

GQA-8 cut KV by 8×. That bought the doc tenant.

Full MHA · 64 KV heads
2.50 MiB/tok
GQA-8 · our model
0.31 MiB/tok
GQA-8 + FP8 KV
0.16 MiB/tok

Bars to scale. Query heads stay 64 — compute is unchanged. Only the KV head count, the thing that multiplies by every token you have ever processed in the sequence, shrinks. That asymmetry is the whole trick.

At MHA prices

One 18.4K doc session would hold ~45 GiB of KV. Our entire per-fleet token budget (slide 6) holds ~391K BF16-GQA tokens — at MHA sizes that is ~49K tokens, under 3 doc sessions. The doc QA tenant does not exist as a product.

The pattern to remember

Architecture choices made for quality reasons (GQA, sliding window, latent KV compression) reappear in production as concurrency multipliers. When you evaluate a model for serving, bytes/token belongs on the first page, next to parameter count.

04 · Per-request footprints

KV grows one token per decode step.

Chat · peak footprint

prompt 350 tok → 114.7 MB at admission
+ 220 decode steps → +72.1 MB
peak at last token: 570 tok

~187 MB

Grid: 36 blocks ≈ the sequence's block allocation over its life — prompt blocks first (coral), decode blocks appended step by step (amber). Small, short-lived, individually harmless.

Doc QA · peak footprint

prompt 18,000 tok → 5.90 GB at prefill
+ 400 decode steps → +131 MB
peak at last token: 18,400 tok

~6.03 GB

32× the chat footprint, and held far longer: prefill plus 400 decode steps at fleet step times is tens of seconds of residence. Capacity is consumed in GB-seconds, not just GB — a long-lived 6 GB hold blocks ~32 chat admissions for its entire lifetime.

Admission must price the peak, not the present. A request admitted at its prompt size will grow by its full output length. Engines that admit on current size alone discover the difference as mid-decode preemption — priced on slide 11.

06 · The TP sharding insight

Tensor parallel does not multiply token capacity.

Per GPU, per token
KV heads per rank = 8 ÷ TP 4 = 2
bytes/token/GPU = 80 × 2 × 128 × 2 × 2
= 81,920 B = 80 KiB

Each rank stores a shard of every token — 2 of the 8 KV heads for all 80 layers. No rank holds a complete token, and no token lives on only one rank.

Fleet token capacity
blocks/GPU = 32.0 GB ÷ (16 tok × 80 KiB)
≈ 32.0e9 ÷ 1.31 MB ≈ 24,400 blocks
tokens = 24,400 × 16 ≈ 391K tokens

Identical on every rank, because it must be: the fleet can hold ~391K distinct tokens total, not 4 × 391K. Adding TP ranks to fit a bigger model does not add a single token of KV capacity — it re-shards the same tokens thinner. Capacity scales with total HBM left after weights, full stop.

Corollary for Chapter 7: for a model that already fits on fewer GPUs, extra TP can reduce effective capacity per dollar — same token ceiling, more ranks burning budget on weights shards and collectives. Parallelism is chosen for latency and fit, never for KV.
07 · Sizing it in vLLM

One flag, one block budget.

# vLLM startup, worked config
--model meta-llama/Llama-3.1-70B-Instruct
--tensor-parallel-size 4
--gpu-memory-utilization 0.90
--block-size 16            # default
--max-num-seqs 256
--enable-prefix-caching

# startup log (the numbers that matter)
GPU KV cache size: ~391,000 tokens
Maximum concurrency (128K ctx): ~3.0x

Log values shown in the form the engine reports them; exact counts come from the profiler run on your hardware and are what the calculator on slide 19 reproduces.

  • The derivation chain: utilisation cap → profiler measures weights + non-KV peak → remainder becomes a block count: num_gpu_blocks = KV_bytes ÷ (block_bytes), where block_bytes already accounts for TP sharding and both K and V tensors.
  • Watermark: the scheduler holds back a small reserve (default watermark = 0.01, ~1% of blocks, ≈244 blocks here) so running decodes can always grow into their next block instead of preempting each other at 100.0% occupancy.
  • max_num_seqs is a second, independent cap: 256 sequences max, even if KV would fit 685 chat sequences. Whichever cap binds first is your concurrency — check both, always.
  • Raising utilisation 0.90 → 0.95 buys 4 GB/GPU ≈ +49K tokens ≈ +2 doc sessions — and spends the fragmentation headroom that keeps long uptimes stable. Priced, not free.
08 · Sizing it in SGLang

A static fraction, a token pool.

# SGLang launch, worked config
--model-path meta-llama/Llama-3.1-70B-Instruct
--tp-size 4
--mem-fraction-static 0.88
--page-size 1              # default; larger ok
# radix cache is on by default

# startup log (the numbers that matter)
max_total_num_tokens: ~391,000
token_to_kv_pool sized to match

The two engines land on the same token ceiling here because the physics is the same; the ~2-point fraction difference is absorbed by different overhead accounting (what each profiler counts inside vs outside the static budget).

  • mem_fraction_static reserves one static pool for weights + KV up front. What remains outside it is the runtime's working space: activations, graph buffers, temporary tensors. Set it too high and the failure is an OOM in the working space, not a smaller cache.
  • The pool is addressed in tokens: TokenToKVPool holds one slot per token; the radix tree maps token sequences onto slot indices. Capacity questions are answered in tokens directly — no block rounding until page size > 1.
  • Two kinds of “used”: slots referenced by running requests (locked via the tree path) and slots held only by cached prefixes (evictable). available + evictable is the real admission budget — the scheduler can always reclaim the evictable part. Slide 13 makes this the accounting model.
Same ceiling, different dials. Porting a capacity plan between engines means translating the budget (utilisation + profiler vs static fraction), not copying the number. A 0.90 pasted into the other engine's flag is a different memory split.

Why averages lie here

Mean context across the mixed trace is meaningless: the distribution is bimodal (570 vs 18,400) and the large mode consumes 32× per unit. Capacity planning on “average tokens per request” under-reserves by the variance, and the variance is the workload.

The operational answers (preview)

  • Tenant quotas on tokens, not requests — a request-count quota lets 21 doc sessions evict the entire chat fleet.
  • Separate pools / replicas per tenant when the mix is adversarial (Chapter 9).
  • Admission control at token budget, with doc QA queueing before chat does (Chapter 4).
11 · Admission, growth, and the price of being wrong

Over-admit, and you pay a full re-prefill.

How engines avoid it
  • Allocate on demand, gate on budget: blocks/slots are taken as tokens actually arrive (prefill chunks, then 1 per decode step), but admission checks the pool can plausibly serve the batch — plus the watermark reserve from slide 7.
  • Decode growth is predictable: exactly 1 token per sequence per step. The scheduler can project exhaustion steps ahead and stop admitting before it arrives. Exhaustion under decode is a policy failure, not bad luck.
  • Prefill is the shock: one 18K admission instantly claims 1,125 blocks. Chunked prefill (Chapter 4) spreads the compute; the KV claim lands with the chunks too — chunking is also an admission-smoothing tool.
When it still happens: preemption, priced
recompute cost (doc victim)
= 2 · 70e9 · 18,000 ≈ 2.52 PFLOPs
+ its queue re-entry delays every SLO
behind it

vLLM frees the victim's blocks and recomputes on readmission (Chapter 2). SGLang's retract keeps the prefix in the tree, so the re-entry is an extend over surviving slots — cheaper if the prefix survives eviction while retracted. Either way: one preemption of a doc session burns roughly the prefill compute of 51 chat requests (18,000 ÷ 350). Watch preemption count as a paging metric, not a curiosity.

12 · Fragmentation, settled with numbers

Paging's waste is 8 tokens per sequence.

Internal fragmentation · the only kind paging has

The tail block of a sequence is partially filled: waste is uniform in [0, 15] tokens, average 8 tokens ≈ 2.6 MB fleet per sequence. At 256 concurrent sequences: ~0.67 GB, about 0.5% of the KV budget. That is the entire fragmentation bill for block size 16.

coral = full blocks dashed = partial tail

What it replaced · contiguous reservation

Reserving max-length buffers per sequence (the pre-paging design, Chapter 2) wastes (max_len − actual_len) per sequence. Reserving 8K for chat sequences that peak at 570 tokens wastes ~93% of every reservation — the fleet would fit ~47 chat sequences in the space paging fills with 685.

  • External fragmentation: paging has none for KV — any free block serves any sequence, any position.
  • SGLang page size 1: tail waste falls to ~0 tokens; page size 16 recovers block-like allocation efficiency at the same 8-token average. The knob trades bookkeeping overhead against single-digit megabytes.
  • Real fragmentation risk lives elsewhere: the utilisation headroom (slide 5) exists for the allocator and workspace, not for KV blocks.
13 · Prefix cache changes the accounting

Three pools. Only one is truly spent.

Locked · runningKV of sequences executing now, plus (SGLang) every node on their matched paths, lock-refcounted to the root. Unevictable. This is the spent pool.
→
Evictable · cached prefixesFinished sequences' KV kept for reuse: full blocks in vLLM's free queue with hashes intact, leaf spans in SGLang's tree. Reclaimable on demand, instantly, by any allocation.
→
Free · never touchedBlocks/slots holding nothing. On a warm production fleet this pool is usually ~zero — and that is healthy, not alarming.
The metric that matters
admission headroom = free + evictable
pressure = locked ÷ total

A dashboard showing “KV cache 99% full” on a warm fleet is showing you a working prefix cache. The paging condition is locked near total while the waiting queue grows — evictions can no longer manufacture room.

The hidden tax

Evictable is not free capacity for planning: admitting against it destroys the cached prefix that made the next request cheap. Every admission that reclaims a hot chat system prompt converts 272–280 saved prefill tokens back into compute — paid by the next chat request's TTFT. Capacity and cache warmth are the same memory, spent two ways.

16 · When prefix caching is worthless

No reuse, no dividend — only displacement.

A cached prefix pays iff  P(reuse before eviction) × prefill_saved > displacement cost — the hits destroyed by evicting whatever held that memory instead.

High-entropy unique prompts

One-shot generation, per-user random seeds, UUID-stamped prompts: divergence at token ~0 past the system prompt. Hit rate collapses to the shared system prompt alone — or to zero if the unique part comes first. Order your prompts shared-first; it is a free hit-rate decision.

Short prompts

A 40-token prompt with a 30-token shared prefix saves 30 tokens of prefill — microseconds — while its cache entry still participates in eviction bookkeeping. Below some prefix length the machinery costs more scheduler time than the compute it saves. The win scales with prefix length × reuse count; both must be non-trivial.

Write-once documents

A doc QA corpus where every document is asked about exactly once: every insert is pure displacement. 18K-token entries evict the hot chat prefix to store KV that will be evicted unread. The fix is policy (don't cache, or partition), not a bigger cache.

17 · Thrash: when the working set outgrows the cache

1.8M tokens of prefixes. 391K of cache.

The scenario, in numbers

corpus churn: 100 distinct docs / hour
× 18,000 tok = 1,800,000 tok working set
cache capacity: 391,000 tok → ratio 4.6×

Under LRU, a prefix re-asked after ~21 other documents have flowed through has already been evicted: the cache cycles ~4.6 times per working-set pass. Steady-state hit rate falls toward the first-touch floor — for repeats arriving uniformly, only requests returning within the most recent ~391K tokens of insertions can hit. Everything else is a cold 18K prefill that also evicts.

Mitigations, in the order to try them
  • Measure the working set first: distinct prefix tokens per hour vs capacity. If the ratio is < 1, you don't have this problem; if it's 4.6×, no tuning below will invent one.
  • Partition by tenant: reserve a token quota the doc churn cannot cross, so chat's 280-token prefix — tiny, extremely hot — is never the eviction victim. Highest value per token in the fleet.
  • Exploit frequency skew: real corpora are Zipfy — if 10 documents take 80% of questions, their 180K tokens fit, and the tail can bypass caching entirely.
  • Buy tokens: FP8 KV doubles capacity (next slide); more HBM is the brute-force version of the same move.
18 · FP8 KV: the 2× capacity lever

Half the bytes. Double the tokens. Read the fine print.

The gain
782K tokens

163,840 B/token → the same 32 GB/GPU holds ≈782K tokens. Doc ceiling 21 → 42 sessions; chat 685 → 1,370 (before the 256 sequence cap binds — slide 7's lesson returns). Decode also reads half the KV bytes per step: TPOT improves where KV read is a visible share of step time, i.e. long contexts and large batches.

The mechanics
  • K and V stored as FP8 (E4M3 typical) with scale factors — per-tensor in vLLM's --kv-cache-dtype fp8 path with calibration scales, per-token/head variants elsewhere. Scales are small but not zero overhead.
  • Attention dequantises on the fly in-kernel; the cost lands on the attention kernel, visible at short contexts where KV bandwidth was never the bottleneck.
  • Only the cache changes dtype here — weights stay BF16 in this chapter's scenario. FP8 weights are Chapter 6, with their own quality gates.
The risk, stated precisely

Quantisation error in KV is not uniform across positions: early tokens and outlier channels carry disproportionate attention mass, and their errors persist for the whole sequence. Perplexity barely moves; long-context retrieval — our doc tenant's golden set — is where degradation concentrates. Rule: FP8 KV ships only after the tenant golden sets pass, per Chapter 6's protocol. Capacity you cannot trust is not capacity.
