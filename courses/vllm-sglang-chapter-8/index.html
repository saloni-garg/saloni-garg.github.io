Speculative Decoding
and Structured Output, Priced

Two features that demo beautifully and bill quietly. Speculation trades extra compute for lower latency only when the draft is right often enough. Constrained decoding trades per-token CPU and capacity for output you can parse. This chapter puts a price on both, per tenant, on the frozen trace.

Framing

Two features, two different kinds of bet

Bet 1 · Latency

Speculative decoding

A cheap drafter proposes γ tokens; the 70B target verifies them in one parallel pass. Accepted tokens are nearly free. Rejected work is pure waste. The payout is a function of acceptance rate α and batch size, and it changes sign: a latency tool at low concurrency, a throughput tax at high concurrency.

Lossless by construction: rejection sampling makes the output distribution identical to plain target sampling. You are buying speed, not trading quality. Chapter 6's gates do not move.

Bet 2 · Shape

Structured generation

A grammar or JSON schema constrains every sampled token. The model can no longer produce unparseable output, so the retry-and-repair loop disappears. The cost is paid elsewhere: mask computation per token, grammar compilation per schema, and CPU that scales with concurrency, not with model size.

Not lossless in the same sense: you are changing the distribution on purpose, zeroing every token the grammar forbids. That is the point, and it interacts with speculation in ways slide 18 prices.

Rule for the chapter: no feature is "on" or "off" globally. Every verdict is per tenant, per engine, at a stated batch regime.

Speculation · The mechanism

Propose γ, verify once, keep the prefix that agrees

Prompt so far: "The capital of France is" · draft proposes γ = 4 tokens, target verifies:

" Paris" "," " which" " sits" draft: " on" bonus: " is"

Three accepted, fourth rejected. The target's own distribution resamples the rejected position (" is" arrives as the correction), and because the target scored one position past the draft, an all-accept step yields a bonus token: up to γ + 1 tokens per target pass.

1 · Draft

γ sequential cheap steps: a small model, prediction heads, or a lookup. Sequential is the catch: draft latency adds, it does not parallelize.

2 · Verify

One target forward pass over γ + 1 positions. At decode batch sizes this is still weight-bandwidth bound, so extra positions are close to free. Close to, not equal to: slide 8.

3 · Accept / resample

Accept each token with probability min(1, p_target / p_draft); on first rejection, resample from the corrected distribution. Expected output: bit-identical distribution to no speculation.

Speculation · The math

Expected tokens per target pass

E[tokens] = (1 − αγ+1) / (1 − α) = 1 + α + α² + … + αγ

If each draft token is accepted independently with probability α, the accepted run length is geometric. Worked for γ = 4 (ceiling: 5 tokens per pass):

Check the endpoints: α = 0 gives exactly 1 (the resampled token, speculation wasted its draft cost). α = 0.7, γ = 4: (1 − 0.16807) / 0.3 = 2.77. The curve is convex in α: going 0.7 → 0.9 buys 48% more tokens per pass; 0.5 → 0.7 buys 43%. There is no regime where a mediocre draft wins big.

Speculation · The cost model

Speedup is a fraction, and both sides move

Speedup = E[tokens] / ( 1 + γ·rd + v(B) )

Numerator: E[tokens]

From slide 4. Set by α and γ. The only term marketing quotes.

γ · rd: draft tax

γ sequential draft steps, each costing rd of a target step. 8B draft, γ = 4: 4 × 0.11 = 0.44. EAGLE: 4 × 0.03 = 0.12. N-gram: ≈ 0.02.

v(B): verify overhead

Scoring γ + 1 positions instead of 1. At batch 1 the weight read dominates and v ≈ 0.08. As batch grows the extra positions become real FLOPs and v climbs toward the compute-bound limit on the next slide.

Worked: chat tenant, 8B draft, γ = 4, batch 1

E = 2.83 (α = 0.71) · denominator = 1 + 0.44 + 0.08 = 1.52 · speedup = 2.83 / 1.52 = 1.86×. TPOT falls from 42 ms to ≈ 22.6 ms per token. Now hold everything fixed and change only the drafter to n-gram at chat's α = 0.25: E = 1.33, denominator 1.10, speedup 1.21×. Same slide-4 formula, a 0.65× spread decided entirely by measured α and rd.

Speculation · The batch regime

Where speculation stops paying

Model of slide 8 with an 8B draft (rd = 0.11, γ = 4); the compute-bound share w = B / (B + 16) interpolates v(B) to its limit, where speedup tends to E / (γ + 1) < 1.

Why the curves bend

Decode at low batch is bandwidth bound (Chapter 4): the verify pass reads the weights once whether it scores 1 position or 5. Speculation is spending idle bandwidth. As batch grows, decode turns compute bound; now every rejected token burned FLOPs that a real token needed. The same γ + 1 positions that were free become a queue.

Read the crossings

α = 0.90 stays profitable to batch ≈ 48. α = 0.70 crosses 1.0× near batch 9. α = 0.50 is a latency win only in the single digits and a throughput loss of nearly 60% at batch 128 (0.42×). A fleet running chat at batch 40+ with a mediocre draft is paying for slower service.

Ship it

Doc QA extractive + n-gram (α 0.81) clears break-even at every batch the tenant actually runs. Chat + 8B draft (α 0.71) clears it only while chat batches stay in the single digits, up to about batch 9.

Gate it

Chat at burst batch 32+ needs α ≥ 0.87 from a model draft. It has 0.71. Speculation must be load-aware: enabled at low concurrency, shed as batch climbs.

Do not ship

Doc QA numeric slice (α 0.49) with any drafter at batch ≥ 8. The verify tax exceeds the accepted-token gain; TPOT and goodput both regress.

# EAGLE: "method": "eagle3" + draft ckpt
  • Speculation is a per-deployment config; one drafter per serving instance.
  • Metrics exported per step: acceptance length and rate land in Prometheus for the Chapter 5 harness.
  • Interacts with chunked prefill: draft steps join the same token budget from Chapter 4.

SGLang

# sglang launch_server
--speculative-algorithm EAGLE
--speculative-draft-model-path <eagle-ckpt>
--speculative-num-steps 3
--speculative-eagle-topk 4
--speculative-num-draft-tokens 16
# or --speculative-algorithm NGRAM
  • EAGLE is the flagship path, with tree speculation: top-k branching drafts a tree of candidates, verified in one pass with tree attention.
  • Tree width trades verify positions for acceptance: 16 draft tokens per step is a different point on slide 8's fraction than a chain of 4.
  • Overlap scheduling (Chapter 2) can hide draft latency behind the previous verify, shrinking the γ·rd term in practice.

Flags as of the pinned versions in Chapter 2's architecture diff. The honest delta: SGLang's tree + overlap story is ahead for EAGLE; vLLM's n-gram and draft-model paths are simpler to operate. Neither changes α. α comes from your text.

Speculation · Measurement discipline

Measuring α without fooling yourself

Do this

  • Log accepted length per step, per request, with tenant and slice tags; α is derived, never sampled from a dashboard average.
  • Measure on the frozen trace replay (Chapter 5), warm and cold prefix cache reported separately: a warm radix tree changes what the draft sees.
  • Report the distribution, not the mean: a bimodal α (0.9 on boilerplate, 0.3 on substance) averages to a fiction.
  • Re-measure after every draft or target upgrade. α is a property of a pair of models on a slice of text.

Not this

  • Quoting the drafter's paper α. Those numbers are measured on the drafter's training distribution, not your tenants' text.
  • Measuring at temperature 0 and shipping at 0.9. Sampling temperature moves α; greedy traces flatter every drafter.
  • Counting the bonus token as draft skill. E includes it; a "per-draft-token acceptance" that silently includes it overstates α.
  • Benchmarking speculation with closed-loop load. At fixed concurrency the batch stays artificially low, exactly where speculation looks best (Chapter 5's trap, again).

Schema addition for bench/: spec: {method, gamma, alpha_by_slice, accept_len_hist} is mandatory in any results file that enables speculation. A speedup number without its α is treated as unmeasured.

Structured output · The mechanism

From JSON schema to a per-token mask

1

Compile

JSON schema → regex → finite-state machine (or a context-free grammar for nested structure). Each state knows exactly which tokens may come next. Compilation happens once per schema, and it is not free: slide 16.

2

Mask

At each decode step, the current state's allowed set becomes a bitmask over the 128,256-token vocabulary. Disallowed logits are set to −∞ before sampling. The model literally cannot pick them.

3

Advance

The sampled token advances the FSM. Strings, numbers, and nesting are tracked character by character inside tokens, so a token is allowed only if every completion of it stays legal.

State: just emitted {"severity": and the schema says an integer 1–5 follows. The vocabulary, masked:

Five tokens survive out of 128,256. Everything else, including perfectly fluent continuations like "high", is zeroed. Correctness of shape is now a runtime guarantee, not a prompt-engineering hope, and the retry loop from the pre-grammar pipeline can be deleted.

Structured output · Per-token cost

The mask is cheap. Knowing the mask is the work

What a step actually pays

  • Mask storage: 128,256 bits = 16 KB per distinct FSM state. Engines precompute masks per state and cache them; a large grammar's state space is the memory line item.
  • Mask application: one elementwise pass over the logits tensor on GPU. Against a 42 ms decode step it is noise, well under 1%.
  • State advance: CPU work per token per sequence: walk the FSM over the sampled token's characters. Microseconds each, but it is serial CPU work multiplied by every sequence in the batch.
  • Indexing: modern backends (XGrammar) precompute a token-trie index over the vocabulary so per-state allowed sets are lookups, not scans.

Jump-forward: the refund

Where the grammar fully determines the next characters, there is nothing to sample. JSON keys, braces, commas, and fixed enum scaffolding are emitted without a model step at all.

Share of tokens that are structural in the doc QA JSON schema
36%

In the running workload's extraction schema, over a third of output tokens are punctuation, keys, and literals the grammar already knows. Jump-forward converts those from decode steps into string appends: constrained output can be faster than free generation for rigid schemas, a fact that surprises teams budgeting it as pure overhead.

Net per-token cost on the frozen trace, example run: +0.4 ms TPOT at batch 8 before jump-forward, −3.1 ms effective after it. Report both numbers; engines differ in how aggressively they jump.

Structured output · The capacity question

Constrained decoding fails at the edges, not the average

Grammar compile latency

A fresh complex schema compiles in tens of ms to seconds depending on size and backend. If schemas are per-request (user-supplied extraction shapes), compile time lands on TTFT and an uncached schema storm is a self-inflicted denial of service. Mitigation: schema cache keyed by canonical schema hash, compile off the request path, admission limits on distinct schemas.

CPU saturation at concurrency

Mask prep and FSM advance run on CPU while the GPU decodes. At batch 8 nobody notices. At batch 128 with per-sequence grammars, the scheduler's CPU budget from Chapter 2 becomes the binding constraint and TPOT degrades even though the GPU has headroom. Profile it as a CPU problem: it will not appear in GPU utilization.

Quality is not untouched

Zeroing tokens renormalizes the distribution. For rigid extraction that is pure win. For schemas imposed on open text (forced enums over nuanced answers), the constraint pushes probability mass onto tokens the model would not have chosen, and the doc QA synthesis slice shows it first. Gate structured output on the golden sets like any precision change (Chapter 6).

Capacity rule: budget grammars like KV cache. Distinct active schemas, states per schema, and CPU per token-step belong in the Chapter 3 capacity calculator, not in a postmortem.

The interaction nobody prices

Speculation × grammar: the mask applies to the draft too

Why α moves under constraint

  • The draft must propose grammar-legal tokens. A draft model that does not know the schema proposes fluent-but-illegal tokens, which are rejected with probability 1: α collapses on exactly the structural spans.
  • Engines handle this by masking the draft's distribution with the same FSM state, so the drafter samples only legal continuations. Then α on structural tokens rises toward 1, because often only one token is legal.
  • Net effect on the extraction workload: constrained α measured higher than free-running α (0.83 → 0.88 on the extractive slice, example run), because the grammar does part of the prediction.

And the traps

  • N-gram + grammar: lookup proposes copied spans that may violate the schema state mid-span; expect shorter accepted runs inside structured regions than the free-running measurement suggests.
  • Jump-forward + speculation: deterministic spans should bypass both. If your engine speculates through spans it could have jumped, you pay draft and verify for tokens that were never uncertain.
  • Verify cost grows: the target's verify pass now also advances γ + 1 FSM states per sequence; the slide 16 CPU term multiplies under speculation at high batch.

Measurement rule, added to the schema: any tenant that runs structured output reports α with the grammar on. Free-running α is a different workload.
