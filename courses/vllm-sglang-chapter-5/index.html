Chapter 5 · Technical Tutorial

Benchmarking Without
Lying To Yourself.

Every number in Chapters 1 to 4 came out of a harness. This chapter builds that harness properly, because the standard way of load-testing an LLM server does not merely add noise to the truth. It systematically reverses it: it ranks the worst configuration first, hides the tenant that is breaching, and reports a throughput no SLO can survive.

The lie

A closed-loop load test throttles itself when the server slows down. The worse the server behaves, the gentler the load it is offered, and the better its latencies look. Coordinated omission, priced on slide 4.

The fix

Open-loop Poisson replay of the frozen trace, cache state controlled between runs, output lengths forced identical, percentiles reported per tenant, and one headline metric: goodput.

Deliverable

The bench/ repo: trace, open-loop runner, analysis, and a results schema that forces method disclosure on every number it emits.

Fixed for this chapter: the Chapter 4 operating point (chunk 512, TP=4, BF16, Llama-3.1-70B on 4 × H100). SLOs unchanged: chat TTFT p95 ≤ 800 ms, chat TPOT p95 ≤ 50 ms, doc completion p99 ≤ 30 s. All benchmark figures are one example run at the pinned engine builds, produced with the protocol in this chapter so you can reproduce, and dispute, every digit. Use ← → or Space to move.

01 · The thesis

A benchmark is an instrument. Most are miscalibrated by design.

Four failure modes account for nearly every misleading serving benchmark in the wild. Each one is a property of the harness, not the engine, and each one biases the result in the vendor's favour.

Lie 1 · Arrival process

Closed-loop clients issue the next request only when the previous one returns. Offered load becomes a function of server speed, so queues can never form in the data, and queueing is where production latency lives.

Lie 2 · Blended percentiles

One histogram for all tenants. Doc QA is 2% of requests in our workload, so a blended p95 is a chat statistic wearing a fleet costume. The breaching tenant is arithmetically invisible.

Lie 3 · Uncontrolled cache state

Prefix cache hit rate drifts upward as a run proceeds. Numbers averaged across cold and warm states describe a system that never existed at any moment during the run.

Lie 4 · Unforced work

If output lengths are sampled live, the two engines generate different amounts of work. The one that stops early wins the throughput chart for doing less.

The standard is not "is this number accurate?" but "could this harness have produced a bad number if the engine deserved one?" A harness that cannot report failure is not measuring. It is marketing with extra steps.
02 · The closed loop, mechanically

Fixed concurrency is a governor on the truth.

The closed-loop contract
N clients · each client: send → wait → send
offered_rate = N ÷ mean_latency

latency doubles → offered rate halves
server stalls → arrivals stop entirely

The load generator and the server form a feedback loop with negative gain: every degradation reduces the pressure that would reveal it. What the harness calls "throughput at concurrency 64" is the server's service rate under self-administered, perfectly smooth load, a traffic pattern no user population has ever produced.

  • No queue can form: with N clients, at most N requests exist. The instant a request would have queued behind 200 others, the harness simply has not created it yet. TTFT measures an empty waiting room.
  • Arrivals are anti-correlated with pain: real traffic bursts hardest exactly when the system is least able to absorb it (retries, failovers, cron-aligned jobs). Closed loop produces the opposite correlation, by construction.
  • Latency is measured on a censored sample: the requests that would have recorded the worst latencies are precisely the ones never issued. The mean improves because the system got slower. That inversion has a name, and it is next.
03 · Coordinated omission, priced

The stall deletes its own victims.

A doc burst saturates prefill and the server effectively stalls for ~1.4 s inside a 10 s window. Watch what each harness issues during the stall, shown as arrivals:

Open loop · Poisson replay at 15 req/s
Closed loop · 64 clients
0 shatched band = server stall ≈ 1.4 s10 s
Intended arrivals in the stall
~21

At 15 req/s, a 1.4 s stall should collect about 21 arrivals. Every one of them experiences the stall in full.

Closed loop records
≤ 64

At most 64 samples of the stall, one per blocked client. Each records one slow request. The arrivals that should have occurred during the stall are never created, so they cannot be slow. They are omitted, in coordination with the failure.

The bias compounds

Percentiles are computed over issued requests. Delete the worst 1.4 s worth of demand from the sample and p95 improves while users wait longer. Longer stall, cleaner chart. This is not a subtle statistical effect; at production stall rates it moves p95 by multiples.

05 · Open loop, done right

Arrivals that ignore the server.

inter-arrival ~ Exponential(λ) · CV = 1
issue at scheduled t, whatever is still running

queue length is an output, never an input

Little's law check: L = λ · W
chat: 12/s × ~3.1 s ≈ 37 in flight
doc:  0.25/s × ~20 s ≈ 5 in flight
Σ ≈ 42 → the batch sizes Chapter 4's sweep saw (40–60)

Poisson is not an affectation. It is the maximum-entropy arrival process for independent users, and its burstiness is the point: at λ = 12/s a 250 ms window expects 3 arrivals and receives 8 or more about 1% of the time. Those micro-bursts are what queues are made of. A harness without them is testing a world without queues.

  • The sanity check is free: Little's law ties arrival rate, latency, and concurrency into one identity. If your harness reports λ and W that imply L = 42 while the server shows 200 running sequences, one of the three numbers is wrong, and now you know to look.
  • Overload is a result, not a crash: offer 20 req/s to a system whose goodput is 15 and the queue grows without bound. The run is not invalid; it is the measurement. Report latency as a function of offered rate, and let the curve confess where the knee is (slide 12).
  • The burst profile stays separate: the frozen trace's 3× burst windows (Chapter 1) are replayed as their own condition and reported as their own row. Folding bursts into a steady-state average is Lie 2 wearing a different coat.
06 · The trace is the experiment

One file. Both engines. No resampling.

# traces/two-tenant-v1.jsonl · generated once, seed 2027
{"t_ms": 0,     "tenant": "chat", "in": 350,  "out": 220,  "prompt": "chat/0417"}
{"t_ms": 83,    "tenant": "chat", "in": 350,  "out": 220,  "prompt": "chat/1093"}
{"t_ms": 4120,  "tenant": "doc",  "in": 18400, "out": 400, "prompt": "doc/007"}
{"t_ms": 4311,  "tenant": "chat", "in": 350,  "out": 220,  "prompt": "chat/2210"}

# arrival times: exponential draws at λ per tenant
# prompt ids index a fixed corpus on disk — same text,
# same token counts, every run, every engine (paired design)
  • Paired comparison: both engines replay the identical file, so run-to-run arrival luck is shared. Differences in the results are engine differences, not different dice. An unpaired benchmark spends most of its variance budget re-rolling arrivals.
  • Token counts live in the trace: in / out are counted with the model's own tokenizer, offline, once. Never estimate tokens as characters ÷ 4: on the doc corpus (JSON and table-heavy) that heuristic errs by up to ±30%, and the error lands directly in your throughput denominator.
  • The corpus is content, not lorem ipsum: prompts are drawn from fixed chat and document sets with realistic prefix overlap (shared system prompt, shared doc corpus), because prefix overlap is what makes the cache a variable worth controlling (slide 10). Random-token prompts would benchmark a cache that never hits.
07 · Force the work to be identical

If the engines do different work, the faster one is just lazier.

# per-request sampling, both engines, from the trace
vLLM   SamplingParams(
         temperature=0, seed=trace.seed,
         min_tokens=out, max_tokens=out,
         ignore_eos=True)
SGLang sampling_params={
         "temperature": 0, "max_new_tokens": out,
         "min_new_tokens": out, "ignore_eos": True}

Every request generates exactly out tokens on both engines. Decode work per request is identical by construction, so a tok/s difference is a speed difference, full stop.

  • The failure mode is silent: with live sampling, output length is a draw from the model's distribution conditioned on the prompt, and small numeric differences between engines (kernel order, sampling implementation) shift where EOS lands. A 6% shorter mean output is a 6% "throughput win" that required no engineering at all.
  • Greedy + seeded: temperature 0 removes sampling variance from latency paths that depend on it (speculative acceptance is Chapter 8's problem; here it would be uncontrolled noise).
  • Forcing is a measurement choice, not a workload claim: real traffic has variable outputs, and Chapter 4's trace already encodes that variability in out. What forcing removes is engine-dependent variability. Quality under each precision is measured on golden sets in Chapter 6, not by this harness.
08 · Warm-up is part of the method

The first minute is a different system.

What is still warming after process start
  • Kernel loading and autotuning: attention and GEMM kernels are selected, loaded, and in places tuned on first shapes seen. Early requests pay costs later requests never see.
  • Allocator growth: the caching allocator expands to its working set in steps; each expansion can stall a step. Steady state begins when allocations stop growing, not when the health endpoint turns green.
  • The prefix cache itself: a "warm cache" run begins only once the corpus is resident (slide 10). Before that, the run is a cold run mislabelled.
protocol (this course, all runs)
discard: first 60 s AND first 200 requests,
whichever ends later · stated in every result file

example run: request #1 TTFT ≈ 8.3 s;
TTFT p50 stable (±5%) after ~50 requests

Warm-up exclusion is not cherry-picking when it is pre-registered in the protocol and reported with the results. It is cherry-picking when the window is chosen after looking at the data, per run, per engine. The difference between rigour and fraud here is a sentence in the method block, written before the run.

09 · Cache state: a controlled variable

Cold and warm are different products.

Metric (example run)Cold cacheWarm cacheWhat changed
Doc TTFT p501.92 s0.81 s~62% of the 18K prompt is prefix hits (shared corpus + system prompt); uncached compute falls from 18K to ~6.8K tokens
Chat TTFT p95486 ms310 msThe 78-token system prompt is small; the cold penalty here is allocator and kernel state riding along, not prefix misses
Doc prefix hit rate0% → climbs during run~62% steadyIn a cold run the hit rate is a function of elapsed time: the run is non-stationary by construction

The rules

  • Report cold and warm as separate rows, never an average. An uncontrolled run that drifts from cold to warm reports ~1.35 s doc TTFT: a number true of no moment in the run.
  • State how the state was produced: warm = corpus replayed once before timing; cold = engine restarted.

Resetting honestly

SGLang exposes a cache flush endpoint; on vLLM at the pinned build the trustworthy cold state is a process restart (or a verified eviction). Whichever you use, prove it: measure the hit rate on the first timed requests. A flush that does not move the hit rate to zero is a rumour, and your cold numbers are warm numbers with worse labels.

10 · Percentiles per tenant, or it didn't happen

The blended histogram erases the doc tenant.

The dashed blended curve is visually indistinguishable from chat's. That is the whole problem, drawn.

doc share of requests = 0.25 ÷ (12 + 0.25) ≈ 2%

blended p95 ← chat's ~p93
blended p98 ← still ~0% doc
the doc tenant exists only above p98

A blended report can show every percentile green while doc completion sits at 45 s against a 30 s SLO, because the breaching population is 2% of the sample and the reported percentiles stop at p95. Percentiles are per-tenant, per-metric, always: TTFT and TPOT for chat, completion for doc, each at p50 / p95 / p99. If a report cannot tell you which tenant a percentile belongs to, it cannot tell you whether an SLO held.

11 · Goodput: the headline metric

Throughput, conditioned on the SLOs.

Schematic from the slide 14 sweep. Past the knee, in-SLO completions fall in absolute terms: overload does not just add latency, it destroys useful work.

goodput = max offered rate λ such that
ALL tenant SLOs hold for the full run

search: binary search on λ · 3 runs per point
verdict: per-tenant percentiles, median run

Peak throughput answers "how fast can it go with no promises?" Goodput answers the production question: "how much load can I sell against these SLOs?" It is a single number per engine per config, it degrades gracefully into cost (Chapter 9 turns it into $/1M tokens), and unlike peak tok/s it cannot be improved by removing the queue from the measurement.

Read the failure shape

Between 15 and 16 req/s, prefill utilisation moves 5 points and TTFT p95 moves 53%. Nothing degrades linearly near saturation; that is the queueing curve from Chapter 1 with measured numbers on it. At 18 /s the offered load exceeds prefill capacity outright: the queue diverges and every percentile becomes a function of when you stopped the run. Numbers from a diverging queue are reported as unstable, never averaged into a table as if they were steady state.

16 · Method disclosure, enforced by schema

A number without its method is an anecdote.

# results/schema.yaml — required fields, run rejected without them
result:
  engine:        vllm @ <pinned commit>  # ENV.lock
  config:        {chunk: 512, tp: 4, kv_dtype: bf16}
  trace:         two-tenant-v1.jsonl (sha256 …)
  arrival:       open-loop poisson replay
  cache_state:   warm | cold   # + how produced
  warmup:        discarded 60 s + 200 req
  output_control: min=max tokens, ignore_eos, temp 0
  generator:     send-lag p99 logged, < 5 ms
  runs:          3 · median · spread reported
  metrics:       per-tenant p50/p95/p99 TTFT, TPOT, completion
  • Environment is data: ENV.lock pins engine commits, driver, CUDA, GPU clock policy (locked clocks for benchmark runs; an unlocked H100's boost variance alone is worth several percent), and host topology. "Same GPU" is not an environment.
  • The generator must prove it wasn't the bottleneck: the runner logs scheduled vs actual send time per request. If send-lag p99 exceeds 5 ms, the client fell behind the trace and the run measured the load generator. That run is void, and the schema makes the voiding automatic.
  • Disclose or delete: any result file missing a field does not render in the report. This is deliberately bureaucratic: benchmarks decay into folklore exactly when the method stops travelling with the number.
17 · The eight-point benchmark audit

Run this on anyone's numbers. Including ours.

  • 1Arrival process stated? Open-loop with a named process, or closed-loop? If closed, every latency is conditional on self-throttled load.
  • 2Cache state controlled? Cold and warm reported separately, with the production method (restart, flush) and a hit-rate proof.
  • 3Work forced identical? Output lengths fixed or their distributions published per engine. Unforced outputs make throughput a sampling artefact.
  • 4Warm-up excluded, window pre-stated? Discard rule written before the run, identical for every contender.
  • 5Percentiles per tenant? Any blended histogram must be accompanied by the per-tenant breakdown, or the smallest tenant is unaudited.
  • 6Generator headroom proven? Send-lag or client CPU logged. A saturated load generator manufactures excellent server latencies.
  • 7Environment locked? Versions, driver, clocks, topology in a file that travels with the results.
  • 8Repeats and spread? At least 3 runs, median and spread reported, seeds fixed. A single run is a story about one afternoon.

Score the vendor post from slide 5 against this list: it fails 1, 2, 4, 5, and 8 outright, and is silent on 3, 6, and 7. Zero of eight. That is the median state of published serving benchmarks, and it is why this course measures everything itself.
