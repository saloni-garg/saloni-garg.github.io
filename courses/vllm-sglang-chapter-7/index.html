Tensor parallel · mechanics

How TP shards a transformer layer

Column parallel, then row parallel

  • QKV and gate/up projections are split by output dimension: each GPU computes a disjoint slice of heads / intermediate features. No communication yet.
  • Output and down projections are split by input dimension: each GPU produces a partial sum of the same output vector.
  • Partial sums must be summed before the next operation can start. That sum is an all-reduce — synchronous, on the critical path, twice per layer.

The counts for Llama-3.1-70B

layers = 80 all-reduces / layer = 2 # attn out + MLP down all-reduces / step = 160 hidden size = 8,192 payload / all-reduce = batch × 8,192 × dtype decode batch 32, BF16 act = 32 × 8,192 × 2 B = 524,288 B (0.5 MiB)

Prefill sends the same all-reduces with batch = token count, so prefill messages are megabytes and bandwidth-bound. Decode messages are kilobytes and latency-bound. Same code path, opposite regimes.

GQA sets a hard floor under useful TP: with 8 KV heads, TP beyond 8 cannot shard KV further — and at TP 8 each GPU holds exactly one KV head, so attention stops shrinking while communication keeps growing.

Tensor parallel · the arithmetic

All-reduce cost per decode step, derived

Ring all-reduce moves 2 × (N−1)/N × payload bytes per GPU. Two terms decide the step cost: bytes (bandwidth) and round trips (latency).

TP degreeRing factorTraffic / GPU / stepLatency term: 160 × per-AR latency
TP22×(1/2) = 1.00×160 × 1.00 × 0.5 MiB = 80 MiB160 × ~5 µs ≈ 0.8 ms (NVLink)
TP42×(3/4) = 1.50×160 × 1.50 × 0.5 MiB = 120 MiB160 × ~6 µs ≈ 1.0 ms (NVLink)
TP8, cross-node2×(7/8) = 1.75×160 × 1.75 × 0.5 MiB = 140 MiB160 × ~15 µs ≈ 2.4 ms (IB) · 160 × ~60 µs ≈ 9.6 ms (100 GbE)

Bandwidth is not the problem

140 MiB per step over NVLink (~900 GB/s peak, several hundred effective) is a fraction of a millisecond. Inside one node, TP's byte volume is nearly free at decode batch sizes.

Latency is the problem

160 sequential, dependent all-reduces cannot overlap with the compute that needs their result. The latency term is a pure additive floor on TPOT — and it is set by the slowest link in the ring, which at TP8 is the inter-node hop.

Tensor parallel · the ceiling

Why TPOT degrades once the model already fits

÷ N

What shrinks: per-GPU weight bytes and per-GPU GEMM work. Decode weight reads halve from TP2 → TP4 — this is the entire benefit, and it saturates at the bandwidth floor from Chapter 6.

const

What does not shrink: the 160 all-reduces, the attention over the full sequence, kernel-launch count, and the scheduler step. Fixed costs are a growing share of a shrinking step.

+ α

What grows: ring participants, synchronization stragglers, and — past the node boundary — per-hop latency. One slow GPU or link sets the step time for all N.

The fit test — run it before reaching for TP

# TP is justified only while at least one is true: 1. weights + minimum KV pool > single-GPU (or smaller-TP) memory 2. per-step weight-read time at current TP > all-reduce latency term 3. single-request context needs KV heads sharded further (TP <= KV heads) # For 70B FP8 on H100: (1) fails at TP4 already — 17.5 GB weights # leave ~50 GB for KV. TP8 here is a capacity choice, never a # latency choice. Price it as one.

Interconnect · inside the node

NVLink is why intra-node TP works at all

900 GB/s

NVLink 4, per H100 SXM GPU, bidirectional aggregate across 18 links. Small-message all-reduce latency ≈ 5–7 µs in NCCL tests at 16 KB–0.5 MiB.

128 GB/s

PCIe Gen5 x16, bidirectional. A PCIe-only node pays ~7× less bandwidth and noticeably higher latency — TP4 on PCIe behaves like a different product.

3.35 TB/s

HBM3, for scale. Even NVLink is 3.7× slower than the memory the weights already sit in. Sharding trades the fastest interconnect in the box for a slower one — it wins only when capacity forces it or bandwidth aggregates.

Procurement consequence: the same engine config is not portable across node types. A TP degree tuned on an NVLink node silently becomes the bottleneck on a PCIe node. Record the interconnect in the benchmark method, next to the engine version — Chapter 5's schema now has a field for it.

Pipeline parallel · mechanics

Pipeline parallel: layers in stages, tokens in flight

PP splits the 80 layers into contiguous stages — PP2 = layers 0–39 and 40–79. Only activations cross between stages, once per microbatch per boundary, instead of 160 all-reduces. The cost is the bubble: stages idle while the pipeline fills and drains.

STAGE 0 · L0–19
STAGE 1 · L20–39
STAGE 2 · L40–59
STAGE 3 · L60–79

Bubble fraction, exact

bubble = (p − 1) / (m + p − 1) # p stages, m microbatches PP4, m=8: 3 / 11 = 27.3% idle PP4, m=32: 3 / 35 = 8.6% idle PP2, m=32: 1 / 33 = 3.0% idle

Decode is the hard case: one token per sequence per step means microbatches are small unless the batch is large — decode bubbles are structurally worse than prefill bubbles.

Where PP genuinely wins

  • Models too large or too oddly shaped for clean TP sharding, where stage transfer (point-to-point, large, rare) beats all-reduce (collective, small, constant).
  • Cross-node links: one activation transfer per stage boundary per microbatch tolerates Ethernet far better than 160 collectives.
  • Combined PP × TP is the standard large-model shape: TP inside the node, PP across nodes — each where its tax is cheapest.

Why DP wins throughput here

70B FP8 fits comfortably at TP4 and serviceably at TP2, so replicas pay zero cross-replica communication during inference. Independent schedulers, independent KV pools, no shared critical path — goodput scales at 0.90–0.97× per added replica in this run, the loss being load-balancer imbalance, not collectives.

What DP gives up

Per-replica ceiling: one 1.24M-token TP8 context becomes four 419K-token TP2 contexts. Prefix caches fragment across replicas — a hot shared system prompt is stored (and hit) per replica, and a request routed to the wrong replica pays full prefill. Routing is now part of the serving system.

Data parallel · the operating details

Replicas are easy to launch and easy to imbalance

Load balancing is a KV problem

Round-robin balances request count, not cost: one 18K doc prefill equals ~50 chat prefills in GPU time. Route on predicted cost (prompt length is known at arrival) and current queue/KV state, or watch one replica saturate while another idles.

Prefix-aware routing

Both engines expose cache state per replica; a router that sends a request where its prefix already lives converts a full prefill into a cache hit (Chapter 2). SGLang's cache-aware router and vLLM deployments behind a KV-aware load balancer both implement versions of this — measure hit rate per replica, not just globally.

DP inside attention: the hybrid

SGLang's DP-attention and vLLM's data-parallel attention variants shard requests across attention groups while keeping MLP tensor-parallel — because with GQA, attention is the part TP scales worst. It is an admission, in code, that pure TP wastes GPUs on KV heads.

Autoscaling granularity follows the replica: DP lets you add 2–4 GPUs at a time. A single TP8 replica scales in steps of 8 — remember this in Chapter 9, when cold-start and step size set the autoscaling policy.

The second node · measured, not assumed

Interconnect reality: the 16 KB message tells the truth

Vendor bandwidth figures come from gigabyte-sized transfers. Decode all-reduces are 16 KB–0.5 MiB, where latency and per-message overheads dominate. Small-message all-reduce latency, ring of 8, NCCL-test style measurement:

On 25 GbE the network term alone is over a third of the entire 50 ms TPOT budget — before a single FLOP. This is why the TP8-on-Ethernet row in the sweep lost to TP4: the model got more parallel and the service got slower, predictably, from this table.

The second node · rules

Three rules for crossing the node boundary

Rule 1

Collectives stay home

Keep all-reduce rings inside NVLink domains. If a collective must cross nodes, it must be on InfiniBand-class fabric with GPUDirect RDMA — and budgeted at the measured latency, not the datasheet bandwidth.

Rule 2

Point-to-point may travel

Pipeline stage transfers and disaggregated KV transfers are large, infrequent, and overlappable. These are the payloads Ethernet and even routed fabrics can carry — priced per request in slide 16.

Rule 3

Replicas need no wire at all

Data-parallel replicas communicate only through the load balancer. When in doubt, the layout with no inference-time network dependency wins on tail latency and failure behavior simultaneously.

Verify your fabric before you benchmark the engines

Disaggregation · the idea

Prefill and decode are two workloads wearing one scheduler

Chapter 4's poisoning problem, restated: prefill is compute-bound and bursty (18K-token doc arrivals), decode is bandwidth-bound and must tick evenly (chat TPOT). Colocated, they share one batch budget and every doc burst is a chat latency event. Disaggregation gives each its own pool:

Router

Classify + route

Request enters; router assigns a prefill worker and reserves a decode slot.

→
Prefill pool · TP4, Node A

Compute the prompt

Chunked prefill at full compute tilt. No decode steps to protect, so no chunk-size compromise.

→
KV transfer

Ship the cache

The request's KV blocks cross the interconnect once — the price of admission, priced next.

→
Decode pool · TP4, Node B

Generate

Decode-only batches: uniform step time, no prefill ever lands mid-batch. TPOT variance collapses.

Independent scaling

Prefill capacity scales with input tokens/s; decode with output tokens/s and concurrency. Our tenants' ratio (long inputs, short outputs for doc QA) is nothing like chat's — sizing one pool for both wastes the difference.

Independent tuning

Prefill pool: large chunks, high batched-token budget, compute-first. Decode pool: small steps, latency-first, larger KV share. Chapter 4's single tuning matrix splits into two, each simpler.

Disaggregation · what it costs

KV transfer: the per-request toll, in bytes and milliseconds

Chat, 570 tokens570 × 163,840 B = 93 MB2.5 ms10 ms39 ms
Doc QA, 18,000 tokens18,000 × 163,840 B = 2.95 GB78 ms311 ms1,230 ms

It's a TTFT tax

Transfer sits between prefill and first token. On IB, 78 ms against an 800 ms chat TTFT budget is payable. On 25 GbE, a doc request spends 1.23 s just moving its cache — paid by a tenant whose SLO is loose (30 s), which is the only reason it survives there.

Prefix caching shrinks it

Blocks already present on the decode side (shared system prompt, repeated document) do not transfer. Warm-cache chat requests can ship near-zero bytes — the transfer cost is proportional to cache-miss tokens, not prompt tokens.

Double residency

During transfer, KV exists in both pools; the prefill pool's blocks free only after handoff completes. Budget both pools for the in-flight set, and count a failed handoff as a full re-prefill — the failure path is recompute, not resume.

The decision tree, keyed to the three inputs

START: smallest TP that fits weights + minimum KV pool?
├─ fits on 1 GPU (≤ ~35B FP8) ────────────→ DP replicas of TP1–2. Never TP for its own sake.
├─ fits at TP2–TP4, one node ─────────────→ DEFAULT: DP replicas at that TP.
│    ├─ two tenants + burst interference breaching SLO → split PD disaggregation (IB)
│    └─ single request needs > per-replica KV pool → raise TP for that pool only
├─ needs TP8+ or PP to fit (≥ ~200B class) → TP inside node × PP across nodes.
│    Collectives never cross on Ethernet. IB is a hard requirement, not a preference.
└─ MoE ───────────────────────────────────→ add expert parallel; rebalance experts before
     adding GPUs — a hot expert makes N GPUs behave like one.

Keyed to model size

Fit decides the minimum TP. Everything above the minimum must justify itself in measured goodput per GPU.

Keyed to context length

Long context inflates the KV pool requirement (forcing TP up) and the disaggregation toll (2.95 GB at 18K, ~10.5 GB at 64K). Both effects are in the tree, in opposite directions — that tension is real, so it is written down.

Keyed to tenant mix

Interference, not load, is the trigger for disaggregation. One tenant or steady traffic: stay colocated and keep the simpler system.

Decision

Parallelism is buying capacity with latency — read the exchange rate

1 · Minimum TP, then replicas

Shard only as much as fit requires. Past that point every added GPU in the ring taxes each token, while every added replica taxes nothing. For this workload: TP4 replicas, 19.9 req/s at 26 ms TPOT on 8 GPUs.

2 · Match the collective to the fabric

All-reduce belongs on NVLink, tolerates InfiniBand, and dies on commodity Ethernet at decode message sizes. Measure your fabric at 16 KB before you benchmark anything else.

3 · Disaggregate for isolation, not fashion

PD separation is burst insurance priced at 93 MB–2.95 GB of KV transfer per request. Buy it when tenant interference breaches SLOs; skip it when traffic is steady.

For this workload, the answer

Two TP4 FP8 replicas across the two nodes as the baseline fleet; disaggregated P/D on InfiniBand as the documented escalation when the doc QA burst profile grows. TP8 stays in the runbook for exactly one job: a future model that does not fit at TP4.
