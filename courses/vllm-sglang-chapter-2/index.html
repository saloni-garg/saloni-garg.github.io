01 · The question of this chapter

Same request in. Different machinery.

Both engines do continuous batching. Both do chunked prefill. Both capture CUDA graphs. If you stop at the feature checklist, they look identical. They are not, and the difference is structural, not cosmetic.

The vLLM bet

The hard problem is memory fragmentation. Solve it with paging: fixed size blocks, a block table per sequence, allocate on demand, never reserve for max length. Reuse across requests is a second system: hash the blocks, cache the hashes.

The SGLang bet

The hard problem is prefix reuse. Prompts in real workloads share long prefixes: system prompts, few shot blocks, documents, chat history. Make the shared prefix the primary object and let allocation follow from it.

How to read this chapter: every design claim is followed by its mechanism: which structure, which function, what it costs per token or per step. If a slide cannot name the mechanism, it does not ship.

03 · vLLM V1 architecture

A separate engine core, a paged block pool.

# process / component map, vLLM V1
API server (FastAPI, OpenAI routes)
  ↓ ZMQ
EngineCore process
  ├─ Scheduler          # admission + token budget
  ├─ KVCacheManager     # block pool + prefix index
  └─ ↓ step outputs
GPU workers (one per rank, TP=4)
  ├─ ModelRunner        # CUDA graphs, attention
  └─ Block tables       # logical → physical
  • Why a separate EngineCore process: the Python scheduler loop never blocks on HTTP handling, tokenisation of the next request, or a slow client. Scheduling latency stays off the API path.
  • The unit of everything is the block: default block_size = 16 tokens. Allocation, sharing, caching, eviction, preemption all operate on whole blocks.
  • Scheduler output per step: a set of requests, how many new tokens each contributes (prefill chunk or 1 decode token), and the block table updates. The GPU executes exactly that.

Source anchors for this chapter: vllm/v1/core/sched/scheduler.py, vllm/v1/core/kv_cache_manager.py, vllm/v1/core/block_pool.py at the pinned commit in the course repo.

04 · SGLang runtime architecture

A tree cache in the middle, an overlapped loop.

# process / component map, SGLang runtime
TokenizerManager        # API + tokenisation
  ↓ ZMQ
Scheduler (per DP rank)
  ├─ RadixCache         # TreeCache: prefix tree
  ├─ ReqToTokenPool     # req → token slots
  ├─ TokenToKVPool      # paged KV allocator
  └─ Grammar backend    # constrained decoding
  ↓
ModelRunner             # forward + CUDA graphs
  ↓ DetokenizerManager → client
  • The tree is consulted before anything is scheduled: match_prefix() on the incoming token ids returns the longest cached prefix and the KV slots already holding it. Prefill is only scheduled for the unmatched suffix.
  • Two level addressing: the radix tree maps token sequences to nodes; each node points into the token to KV pool, which is itself paged (default page size 1 token, larger pages configurable).
  • The scheduler loop overlaps by design: batch N+1 is prepared on CPU while batch N runs on GPU. That is a first class mode (enable_overlap_schedule), covered on slide 15.

Source anchors: python/sglang/srt/managers/scheduler.py, python/sglang/srt/mem_cache/radix_cache.py, python/sglang/srt/mem_cache/memory_pool.py at the pinned commit.

05 · PagedAttention, mechanically

KV as pages. Fragmentation near zero.

The problem it solved

Pre paging systems reserved a contiguous KV buffer per sequence sized for max possible length. A chat request that ends at 220 output tokens reserved room for thousands. Measured waste in early systems: 60 to 80% of KV memory held nothing. Utilisation looked full; concurrency was starved.

blocks(seq) = ceil(tokens / 16)
chat 350 tok → 22 blocks · doc 18,000 → 1,125 blocks
internal waste ≤ 15 tok/seq ≈ ≤ 4.9 MB total KV*

*At 0.33 MB per token fleet wide from Chapter 1. Average waste is half a block, about 8 tokens per sequence. Compare: the old reserve worst case wasted the entire unused reservation.

One sequence, animated

24 blocks holding 380 tokens: an 18 block prompt (288 tok) plus 92 generated tokens. The block table is the indirection: logical blocks 0 to 23 map to physical blocks scattered anywhere in the pool. Attention kernels gather via the table; contiguity is never required.

coral = prompt blocks amber = generated blocks dashed = partial tail (12 of 16 slots)

06 · Inside the block manager

Allocate, share, preempt: block rules.

Allocation

Free queue, O(1) pop

Free blocks live in a doubly linked free queue. Allocation pops from the head; freeing appends. A decode step needs at most one new block per sequence, only when the tail block fills. Allocation cost never scales with pool size.

Sharing

Refcounts + copy on write

Sequences that share a prefix (parallel samples of one prompt, beam candidates, cached prefixes) point at the same physical blocks with a refcount. The first write to a shared block triggers a copy. Reads never copy.

Preemption

Recompute, not swap

When the pool runs dry mid decode, the lowest priority running sequence is preempted: its blocks are freed and it rejoins the waiting queue. On readmission its KV is recomputed from the prompt. V1 dropped swap out to CPU: recompute on H100 is cheaper than PCIe round trips at these sizes.

The cost model to remember: preemption is not free, it is a bet. Cost of preempting a doc QA sequence ≈ one full 18K re-prefill. Cost of never preempting is head of line blocking for everyone. The scheduler's priority order is where that bet is placed, which is why Chapter 4 returns to it.
07 · vLLM prefix caching, honestly

A hash chain over blocks.

# block hash, chained (simplified)
h[-1] = hash(request salt, LoRA id, ...)
for block i in prompt blocks:
    h[i] = hash(h[i-1], tokens[i], extra keys)
    lookup h[i] in cached_block_hash_to_id
    if miss: stop # chain breaks here

# only FULL 16 token blocks are hashable
# the partial tail block is never shared

Chaining is the correctness trick: a block hash encodes its entire prefix history, so two identical 16 token chunks at different positions never collide into a false share.

What this buys on our workload
  • Chat: 280 token shared system prompt = 17 full blocks cached after the first request. Every later chat skips prefill for those 272 tokens (17 × 16), computes only the tail.
  • Doc QA: a re-asked question on the same 18K document hits on every full block of the document prefix. Near total prefill skip.
  • Eviction: cached blocks sit in the free queue and are evicted least recently used first when allocation needs them. A hit moves the block out of the evictable set and bumps its refcount.
  • The limit: granularity is 16 tokens and full blocks only. A prefix that diverges mid block shares nothing past the last full block boundary.
08 · RadixAttention, mechanically

The cache is a tree of token sequences.

Edges are compressed: one node holds a whole token span, not one token. A node splits only where sequences diverge. Insert, match, and evict all walk this tree.

  • match_prefix(key): walk from the root comparing token spans; return the longest matched path and its KV slot indices. Cost is proportional to the matched prefix structure, not to total cached tokens.
  • Granularity: matching works at token level (page size 1 by default), so a prefix diverging at token 273 still shares 272. No full block requirement.
  • Insert on completion: finished sequences insert their full path. The tree deduplicates against existing nodes, splitting where the new path diverges.
  • Every tenant pattern is one structure: shared system prompts, multi turn history (each turn extends the previous path), few shot prompts, and document reuse are the same walk.
09 · Radix eviction and locking

Evict leaves. Never evict a running path.

The eviction rule
  • Only leaf nodes can be evicted. Evicting an internal node would orphan its children and destroy longer shared prefixes.
  • Leaves are kept in a heap ordered by last_access_time: eviction is LRU over leaves. After a leaf is evicted, its parent may become a leaf and enter the heap.
  • evictable_size_ is tracked incrementally: the scheduler knows exactly how much memory it can reclaim before it asks.
The locking rule
  • When a request starts, inc_lock_ref() walks its matched path to the root. Locked nodes are unevictable, even if they are leaves.
  • On finish or abort, dec_lock_ref() releases the path. This is a refcount per node, exactly analogous to vLLM block refcounts, one level up in abstraction.
  • Failure mode this prevents: a long doc QA decode holding a 16.5K prefix for 25 seconds while chat traffic churns the cache. Without locking, its own prefix could be evicted out from under it.
Contrast worth memorising: vLLM evicts whole cached blocks from a free queue, LRU. SGLang evicts whole leaf spans from a tree, LRU, with path locking. Same policy family, different unit: 16 token block vs variable length span.
10 · KV systems, head to head

Block index vs tree.

PropertyvLLMSGLang
Primary structureBlock pool + block table per sequenceRadix tree over token sequences
Allocation unitBlock, 16 tokensKV slot, page size 1 token (configurable)
Sharing unitFull blocks only, via chained hashAny matched prefix span, token granular
LookupHash chain walk, stops at first missTree walk from root, longest match
Eviction unitWhole block, LRU in free queueWhole leaf span, LRU heap over leaves

Neither is free. The hash walk is O(blocks in prompt) with tiny constants and no tree maintenance. The tree walk touches fewer, larger nodes but pays split and merge bookkeeping on every insert. 12 · R through vLLM

Hash the blocks. Compute 78 tokens.

1
Tokenise + enqueue. 350 token ids enter the waiting queue, FCFS behind 6 others.
2
Hash chain lookup. 21 full blocks in 350 tokens (336 tok). Blocks 0 to 16 hit (272 tok of system prompt). Block 17 misses: it straddles the system to user boundary. Chain stops.

Allocate. Cached blocks get refcount bumps, no copy. New blocks allocated for the remaining 78 tokens plus decode growth.
4
Schedule + prefill. Scheduler grants a token budget slice alongside 38 running decodes. Prefill computes 78 tokens only: 272 are read from cache.

13 · R through SGLang

Walk the tree. Compute 70 tokens.

1
Tokenise + enqueue. TokenizerManager forwards 350 ids to the scheduler.
2
match_prefix(). Tree walk matches the full 280 token system prompt span exactly, token granular. Returns the node path and its KV slot indices. No boundary loss.
3
Lock the path. inc_lock_ref from matched leaf to root. Those slots are now unevictable for R's lifetime. Slots for 70 new tokens allocated from the token to KV pool.
4
Extend prefill. The batch is built as an extend batch: prefix length 280, extend length 70. Attention reads cached KV for the prefix, computes QKV for 70 tokens only.
5
Decode + insert. Each step appends one slot. On completion the full path (prompt plus generated text) is inserted into the tree for the next request, locks released.
The honest delta on R
8 tokens

That is the whole prefill difference on this request: 78 vs 70 tokens computed, from token granular matching vs full block matching. Worth about 2 to 3 ms of prefill. Real, and small.

The delta grows when prefixes are short, unaligned, or highly branched (many tenants, many system prompt variants), and shrinks to zero when prefixes align to block boundaries. Anyone quoting a single cache speedup number without the prefix distribution is selling something.

Where the architectures separate at scale is not this 8 token tax. It is hit rate under churn and scheduler behaviour under pressure: the next two slides.

14 · The vLLM scheduler loop

One token budget, spent every step.

# scheduler step, V1 (simplified)
budget = max_num_batched_tokens
for req in running:        # decodes first
    grant 1 token; budget -= 1
for req in waiting:        # then admissions
    need = min(req.remaining_prefill, budget)
    if blocks available:     # KV gate
        grant need (chunked); budget -= need
    if budget == 0: break
execute step → append outputs → free finished

This loop is the heartbeat: every engine step re-runs it. Step time = GPU forward + this loop's CPU time, serially, unless overlapped.

  • Decodes are privileged: running requests claim their 1 token each before any new prefill is admitted. That ordering is what keeps TPOT stable as load rises.
  • Chunked prefill falls out of the budget: an 18K doc prefill with a 4,096 token budget (illustrative setting) is admitted across at least 5 steps, interleaved with decodes. Chapter 4 sweeps this knob.
  • Admission is KV gated: no blocks, no admission, even with budget left. This is the mechanism that turns KV headroom (Chapter 1, number 4) into queue wait.
  • Priority: default FCFS by arrival. Priority scheduling exists; with it, preemption follows the same order in reverse.
15 · The SGLang scheduler: overlap + retract

Prepare batch N+1 while N runs.

CPU
build batch N
build batch N+1
build N+2
GPU
forward N
forward N+1
fwd…

Serial loop (vLLM style): step time = CPU build + GPU forward. Overlapped: step time tends toward max(CPU build, GPU forward). The saving is the scheduler's own latency: batch construction, tree walks, grammar state, sampling prep. It matters most at small batch and short steps, where CPU time is a visible fraction of step time. The trick that makes it possible: batch N+1 is built against future token ids, resolved when batch N's sampled outputs land.

Under memory pressure: retract

Instead of preempt and recompute one victim, the scheduler can retract running requests back to the waiting queue and shrink the batch, releasing their decode slots while keeping prefix state in the tree. Retracted work re-enters as an extend against the warm tree, so re-prefill is cheaper than a cold recompute when the prefix survives.

Batch formation

Prefill admission respects a token budget and a rem_total_tokens check against allocator plus tree evictable size. Running decode batches and extend batches are formed separately, then merged under the per step limits. Grammar constrained requests carry their state through the same path (next slide).

16 · Structured output lives in the runtime

Grammars are a scheduling input.

SGLang: constraint native
  • Born as a programming runtime for structured generation: JSON schema, regex, and EBNF grammars compile to a finite state machine in the grammar backend (xgrammar class).
  • Per step, the FSM produces a vocabulary mask; masked logits make invalid tokens unsamplable. Jump forward: when the FSM has exactly one legal continuation string, those tokens are emitted without a model step per token.
  • Constraint state is per request in the scheduler, so it composes with radix caching and overlap rather than sitting behind the API.
vLLM: guided decoding layer
  • Guided decoding (JSON schema, regex, choice, grammar) is integrated into the sampling path with the same class of backend libraries, applied as a logit mask per step.
  • Functionally convergent for standard JSON mode workloads. The architectural difference is heritage and depth of integration, not a capability checkbox.
  • Shared cost model: mask construction is CPU work per step per constrained request. At high concurrency it eats the same scheduler budget slide 15 overlaps away. Chapter 8 prices this properly.
Precision note: constrained decoding guarantees syntactic validity only. A schema valid answer can still be wrong, incomplete, or refused content in valid JSON. Structure is a contract on shape, never on truth.
17 · The convergence audit

What is no longer a difference.

Converged · do not pitch these
  • Continuous batching: both, foundational
  • Chunked prefill: both, budget driven
  • Prefix caching: both, different structures (this chapter)
  • CUDA graphs for decode: both
  • Paged KV allocation: both (SGLang's pool is paged too)
  • OpenAI compatible serving API: both
  • Speculative decoding hooks: both (priced in Chapter 8)
Still genuinely different
  • Cache as tree vs cache as block hash index: granularity, eviction unit, insert cost
  • Scheduler overlap as a first class loop mode
  • Pressure response: preempt and recompute vs retract into a warm tree
  • Structured generation depth in the core runtime
  • Frontend heritage: serving engine vs programmable runtime with a serving layer
Why convergence happened

These were never ideology. Chunked prefill, graphs, and paging are forced moves by the physics from Chapter 1: prefill is compute bound, decode is bandwidth bound, KV is the capacity limit. Two competent teams given the same roofline arrive at the same moves. The remaining deltas are bets about workload shape, mainly how much prefix sharing your traffic actually has.

18 · Reading the deltas as workload bets

Which structure wins depends on your prefixes.

High sharing traffic

multi turn chat · agents reusing tool context
shared docs · few shot heavy · many tenants,
many system prompt variants

Prefix reuse dominates the cost model. Token granular tree matching, path locking, and retract into warm state all compound. Measure: prefix hit tokens as a fraction of total prompt tokens on your trace.

Low sharing traffic

unique prompts · high entropy inputs
one shot generation · minimal system prompts

Prefix machinery earns little either way; both engines fall back to raw paging plus scheduling quality. The block hash walk's lower bookkeeping overhead is a small, real edge, and the decision moves to ecosystem, kernels, and operability, which Chapter 9 scores.

Our frozen workload sits between the poles: chat is high sharing (80% of prompt tokens are the shared prefix), doc QA is high sharing per document but with few, huge prefixes. That mix is exactly why Chapter 3 measures hit rate per tenant instead of quoting one number for the fleet.
