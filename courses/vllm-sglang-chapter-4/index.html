Chapter 4 · Technical Tutorial

Batching, Prefill, and the
TTFT / TPOT Trade.

Prefill is a compute job. Decode is a bandwidth job. The scheduler forces both onto the same GPU, one token-budgeted step at a time — and every latency number in this course is the residue of that arbitration. This chapter derives both sides from the hardware, then sweeps the one knob that trades them against each other.

The physics

One ridge number decides which phase is which: 989 TFLOPS ÷ 3.35 TB/s ≈ 295 FLOP/byte. Decode lives far below it, prefill far above it.

The conflict

One unchunked 18K doc prefill is a ~1.4 s stall injected into every co-running chat token stream. Chunked prefill is how you slice that stall — not how you delete it.

Deliverable

A tuning matrix: chunk size × token budget × tenant mix, from a sweep at 512 / 2,048 / 8,192 on both engines over the frozen trace.

Workload unchanged: Llama-3.1-70B-Instruct, 4 × H100 80GB, TP=4, chat (350 in / 220 out) and doc QA (18K in / 400 out). SLOs frozen in Chapter 1: chat TTFT p95 ≤ 800 ms, chat TPOT p95 ≤ 50 ms, doc completion p99 ≤ 30 s. Use ← → or Space to move.

01 · The thesis

Two phases. Two different bottlenecks.

Prefill · a compute job
140 GFLOP / token

Every prompt token is processed in parallel through every layer: FLOPs ≈ 2 × N × tokens (N = 70B params), plus an attention term that grows quadratically in context. The weights are read once for the whole prompt. Prefill speed is set by the fleet's 3.96 PFLOP/s BF16 ceiling — and by how close your kernels get to it (MFU).

Decode · a bandwidth job
35 GB / step / GPU

Each step produces one token per sequence and must read all the weights plus all the KV of every running sequence to do it. FLOPs per step are trivial; bytes are not. Decode speed is set by 3.35 TB/s of HBM bandwidth per GPU — the step cannot finish until the weights have streamed past.

Everything in this chapter is arbitration between these two jobs. A scheduler step that spends its budget on prefill tokens is buying TTFT with other requests' TPOT. There is no configuration where both are free — there are only configurations where the trade is explicit, measured, and priced per tenant.
02 · The roofline, in H100 numbers

Ridge point: 295 tokens per weight pass.

Per GPU, BF16 dense, schematic log–log. Achievable = min(989 TFLOPS, intensity × 3.35 TB/s).

ridge = peak FLOPS ÷ bandwidth
= 989e12 ÷ 3.35e12 ≈ 295 FLOP/byte

decode intensity ≈ batch size
(each weight byte serves B tokens)

prefill intensity ≈ prompt tokens
(each weight byte serves the whole chunk)

Read the chart as a staffing decision. Decode at batch 1 uses 0.3% of the GPU's arithmetic — it is a memory system with a model attached. It only approaches the roof near batch ~295. Prefill is born on the roof: a 2,048-token chunk has intensity ~2,048, seven times past the ridge. Same silicon, opposite scarcities — which is why one scheduler knob cannot optimise both.

Bars to scale by bytes read per step. Bandwidth-floor times; real steps add sampling, scheduling, and kernel overhead on top.

The batching dividend

Going B=1 → B=64 raises step time by 8% (10.5 → 11.3 ms) and multiplies decode throughput by ~60× (95 → ~5,600 tok/s fleet). The weights pass is already paid; extra sequences ride it for the price of their KV reads alone. This is the entire economic case for continuous batching, in one subtraction.

The long-context tax

At doc context, KV read is 96.5 GB of the 131.5 GB step — 73%. Sixty-four doc decodes run at 39 ms/step, inside chat's 50 ms TPOT budget but with no headroom for a prefill chunk in the same step. Context length is a TPOT variable, not just a capacity variable (Chapter 3): the same bytes are paid again every single step.

04 · Prefill time, derived

One doc prefill: ~1.4 seconds of fleet.

1
Dense term: 2 · 70e9 · 18,000 = 2.52 PFLOPs. Every prompt token through every weight, once.
2
Attention term: 2 · L² · d · layers ≈ 0.43 PFLOPs at L=18K — ~17% on top of dense, and the only term that grows quadratically. At 128K it is larger than the dense term (slide 18).
3
At realistic MFU: prefill kernels on a mixed production build run at ~45–50% of the 3.96 PFLOP/s roof → effective ≈ 1.9 PFLOP/s → 18K prefill ≈ 1.4 s, i.e. ~13K tokens/s of prefill throughput.
4
Chat for scale: 350 tok ≈ 26 ms of compute. A chat TTFT is mostly queueing and scheduling, not arithmetic — which is why chat TTFT collapses when something else owns the step loop (slide 11).
prefill_time(T) ≈ (2·N·T + 2·L²·d·layers) ÷ (MFU × 3.96 PFLOP/s)

T = 18,000 → ≈ 1.4 s
T = 2,048 (one chunk) → ≈ 160 ms
T = 350 (chat) → ≈ 26 ms

Hold the 1.4 s in mind. It is 28× the chat TPOT budget and 1.75× the chat TTFT budget. If those 18K tokens are ever admitted as one indivisible step, both chat SLOs are broken by construction — no tuning of anything else can save them. The rest of the chapter is about never letting that happen by accident.

05 · What continuous batching replaced

Static batching: the longest request sets the price.

One static batch · output lengths from the trace

req A · 18 tokens out
req B · 220 tokens out
req C · 64 tokens out
req D · 400 tokens out

slot utilisation = (18+220+64+400) ÷ (4 × 400)
= 702 ÷ 1,600 = 44%

A finishes at step 18 and its slot idles for 382 steps. Nothing new is admitted until D finishes — the batch is the unit of admission, completion, and release. More than half the decode slots in this batch produce padding-shaped nothing.

The three structural wastes
  • Straggler waste: output lengths in real traffic vary by ~20× (18 vs 400 above). A request-level batch retires at the max, so waste scales with the variance, not the mean — and the variance is the workload (Chapter 3's lesson, second appearance).
  • Formation wait: a request that arrives just after a batch launches waits for the entire batch before its prefill can even start. TTFT inherits batch duration, not queue depth.
  • Memory held hostage: finished sequences' KV (Chapter 3: up to ~187 MB per chat sequence) stays allocated until the batch retires, shrinking the pool for everyone else.

Both engines in this course abandoned this model years ago. It is worth one slide because every "just batch the requests" intuition formed on offline inference dies here.

06 · Continuous batching, mechanically

The batch is rebuilt every step.

Iteration-level scheduling: the unit of admission and release is one decode step, not one request. Watch the composition change — sequences join the step they are admitted, leave the step they finish, and their KV is freed in the same iteration.

Step n
A B C
Step n+1
A B C +D
Step n+2
A B C D +E
Step n+3
B C D E
Step n+4
B C D E +F
Step n+5
B D E F +G

No padding

Variable lengths are handled by varlen attention kernels over packed tokens, not by padding sequences to a common length. The 44% slot utilisation of slide 6 becomes ~100% of admitted work — waste moves from the batch to the admission policy, where it can be managed.

Latency becomes per-token

With admission at every step boundary (~11 ms at chat batch sizes), a new request's wait to enter the batch is one step, not one batch lifetime. Formation wait — the static model's TTFT floor — effectively disappears.

The scheduler is now the product

Once the batch is rebuilt every step, who gets tokens in this step is a decision made ~90 times a second. The rest of this chapter is that decision: budgets, priorities, and what happens when a prefill asks for 18,000 tokens at once.

07 · Anatomy of one scheduler step

Four stages. One token budget.

1 · Schedule (CPU)Walk the running set: each decode claims 1 token. Spend the remaining budget on prefill (waiting requests, in policy order). Allocate KV blocks/slots for everything scheduled.
→
2 · Forward (GPU)One fused pass over the packed token batch: decodes and prefill chunks together, varlen attention, each sequence attending only to its own KV.
→
3 · SampleOne next token per sequence in the batch — decode sequences advance, a finished prefill chunk hands its sequence to decode (or schedules its next chunk).
→
4 · BookkeepFinished sequences release KV and leave. New arrivals become eligible. Metrics emitted. Loop — at chat batch sizes, ~90 times per second.
The CPU is in the loop

Stages 1 and 4 run on CPU while stage 2 runs on GPU. If scheduling a step costs 2 ms of CPU and the GPU step is 11 ms, an unoverlapped loop wastes ~15% of the fleet. This is why SGLang's overlap scheduling (Chapter 2: schedule step n+1 during step n's forward) and vLLM V1's async scheduling exist — they hide the CPU inside the GPU's shadow. At large batches the GPU step grows and the overlap stops mattering; at chat batch sizes it is worth real TPOT.

The token budget is the constitution

Stage 1 enforces one invariant: Σ tokens this step ≤ budget. Every policy in this chapter — chunked prefill, priorities, tenant gates — is a rule for dividing that budget. When you read either engine's scheduler source (Chapter 2), this loop and this invariant are what you are reading.

08 · The mixed step, in arithmetic

Decode is non-negotiable. Prefill gets the change.

step_tokens = running_decodes × 1 + prefill_tokens
step_tokens ≤ budget

prefill_tokens = budget − running_decodes

budget 2,048, B = 64 → prefill gets 1,984
budget 512,   B = 64 → prefill gets 448
budget 512,   B = 512 → prefill gets 0

Decode-first is not a preference, it is physics: a running sequence that misses its step has its TPOT slip by the full step time, and it slips for every running sequence at once. A waiting prefill that misses a step loses a few milliseconds of TTFT. The asymmetry decides the priority order on both engines.

  • The starvation trap: the third line above is a real configuration failure. If running decodes can consume the whole budget, prefill never runs: new requests queue forever behind a busy decode set, TTFT goes to infinity while TPOT looks perfect. Budget and max-num-seqs / max-running-requests must be set together, with headroom reserved for prefill.
  • Semantics differ — read your engine: vLLM's --max-num-batched-tokens caps the total step (decodes included), so the formula above is literal. SGLang's --chunked-prefill-size caps the prefill portion; decodes ride on top in the mixed batch. The same number, 2,048, is a different step size on the two engines.
  • Chunk ≠ budget: the chunk is how much of one prompt may be scheduled per step; the budget is the step total. With several waiting prompts, the budget can be split across several chunks — or spent on one. Policy again.
09 · Chunked prefill, mechanically

18,000 tokens, admitted 512 at a time.

The doc prompt as 36 chunks of 512

Each cell is one chunk scheduled in one step, alongside the running decodes. Chunk k attends to the KV of chunks 1…k−1 — causality is preserved, the prompt is simply built incrementally. At chunk size 2,048 the same prompt is 9 chunks; at 8,192, three.

decodes keep flowing between chunks
  • KV lands with the chunks: each scheduled chunk claims its KV immediately — 512 tokens = 32 blocks of 16 (Chapter 3). The full 18K claim (1,125 blocks) is spread over the prefill's whole duration instead of landing in one step, so admission pressure is smoothed in memory as well as in compute.
  • The re-read cost is small: chunk k's attention reads the prefix KV built so far. Summed over all chunks at C=512 that is ~26 GB per GPU of extra HBM traffic — under 10 ms across the entire prefill. Chunking is not expensive in bandwidth; its costs are kernel efficiency at small chunk sizes and step-count overhead.
  • Who chunking does not help: the chunked request itself. The doc's TTFT is still its full prefill time, plus queueing behind other chunks. Chunking is a neighbourliness mechanism — it protects everyone else's latency from your prompt, at a small price to your own completion time (priced in the sweep, slide 14).

11 · What chunking can and cannot do

Chunking redistributes the stall. It never deletes it.

512
Chunk size
36
Chunks per 18K doc
≈38 ms
Stall per mixed step
≈1.37 s
Total stall · conserved

Stall per mixed step = chunk × 140 GFLOP ÷ 1.9 PFLOP/s effective (slide 5), charged to every co-running decode in that step. The product — chunks × stall — is the doc's prefill time at every setting. The knob chooses the shape of the pain: one 1.4 s freeze, or 36 interruptions of ~38 ms, or 3 of ~600 ms.

What the shape buys you

SLOs are percentile contracts. A 38 ms stall folded into an 11 ms decode step yields ~49 ms tokens — at the edge of the 50 ms TPOT budget. A 600 ms stall yields tokens no percentile below p100 can hide. Chunk size is chosen against the TPOT percentile, not against throughput.

What it cannot do

  • Reduce total prefill compute by one FLOP — the doc still costs ~2.95 PFLOPs.
  • Improve the chunked request's own TTFT.
  • Help when many docs queue: 36 polite chunks from each of 12 docs is still 12 doc prefills of load (Chapter 3's tenant arithmetic, in time instead of memory).

14 · Reading the sweep

Three findings. One frontier.

Finding 1 · The chunk is an SLO decision

Chat TPOT p95 moves 1,380 → 47 ms across the sweep — a 29× range from one integer. Nothing else in either engine's flag set moves a production SLO by 29×. If you tune one thing after this chapter, it is this, and you tune it against the TPOT percentile at your real tenant mix.

Finding 2 · The tenants pay each other

Doc p99 completion degrades 14.2 → 24.6 s (+73%) as the chunk shrinks: smaller chunks interleave more decode steps and run prefill kernels less efficiently. Chat's safety is purchased with doc latency, on the same GPU, in the same budget. The matrix on slide 19 exists so this price is chosen per deployment, not discovered per incident.

Finding 3 · Engines converge, settings don't

At matched settings the engines sit within ~5% of each other on every metric. SGLang's edge at 512 (44 vs 47 ms TPOT) is its overlap scheduling hiding CPU time inside short steps (slide 8) — real, and worth ~3 ms. The 29× is the chunk. Configuration is a bigger lever than engine choice in this chapter's regime — Chapter 2's architectural deltas show up elsewhere (prefix-heavy loads, structured output), not here.

The knee is at 512 for this workload, not in general. It sits where chunk stall (~38 ms) + decode step (~11 ms) ≈ the TPOT budget (50 ms). On a smaller model, a faster GPU, or a looser SLO, the knee moves — the derivation (slides 3–5) is how you find yours without sweeping blind.

16 · When chunking is not enough: fixes two and three

Gate the prefill. Or give it its own GPU.

Fix 2 · Priority + admission gating
  • Tenant priority in the scheduler: doc chunks are scheduled only from budget left over after chat decodes and waiting chat prefills. Chat never queues behind a doc chunk it didn't arrive before.
  • Prefill admission gate: at most 1 concurrent doc prefill per replica. Additional docs wait at the router/load balancer — where queueing is visible, measurable, and cheap — instead of inside the step loop, where it is invisible and billed to chat's TPOT.
  • What it fixes: the multi-doc pile-up (slide 12's third bullet). Chunking shapes one prefill; the gate bounds how many prefills may be in flight at once.
Fix 3 · Separate the pools
  • Dedicated replicas per tenant: doc QA gets its own replica(s) where unchunked, max-MFU prefill is correct behaviour; chat replicas run small budgets and never see an 18K token.
  • The cost: you lose statistical multiplexing — a doc replica idles between doc bursts, a chat replica cannot borrow its FLOPs. Isolation is bought with utilisation, always.
  • The grown-up version is prefill/decode disaggregation — separate pools, one fleet, KV transferred between them. That is Chapter 7, with its transfer costs priced. Fix 3 here is the same idea with a load balancer instead of a KV fabric.
Order of operations: chunk first (free, one flag), gate second (policy, no hardware), separate last (hardware, real money). Most production incidents attributed to "the engine" are the first two steps never having been done.
17 · Where this chapter's tools run out

At 128K, the quadratic term takes over.

Prefill at 128K context
dense: 2 · 70e9 · 131,072 ≈ 18.3 PFLOPs
attention: 2 · L² · d · layers ≈ 22.5 PFLOPs
total ≈ 40.8 PFLOPs → ≈ 21 s at 1.9 PFLOP/s

Chunked at 512, that is ~256 chunk-steps of interference spread over 21+ s. No chunk size makes a 128K prefill neighbourly; the request class itself has changed. This regime is served by prefix caching (Chapter 3: a cached 128K prefix is 21 s you never spend), a dedicated long-context pool, or disaggregation — not by scheduler tuning.

Decode at 128K context
KV read / seq / step = 131,072 × 80 KiB ≈ 10.5 GB/GPU
batch of 8 → 84 GB + 35 GB weights
step ≈ 36 ms before any prefill shares it

Eight long-context decodes nearly exhaust the TPOT budget on KV reads alone. Long-context serving is bandwidth economics end to end — which is why FP8 KV (Chapter 3: halves every one of these reads) and KV-sparse attention variants matter more at 128K than any scheduler policy in this chapter.

Know which regime you are in before reaching for a knob: ≤ ~32K contexts, scheduling is the lever; beyond that, memory traffic is. The frozen workload lives deliberately in the first regime — it is where most production chat + RAG traffic actually sits.

19 · Chapter close

The step budget is the SLO, divided up.

Decided in Chapter 4

  • Prefill is compute-bound (140 GFLOP/token, ridge 295), decode is bandwidth-bound (35 GB + KV per step): every scheduling rule follows from that asymmetry
  • Chunked prefill at 512 is the frozen workload's operating point — the only swept config where both chat SLOs hold on both engines, bought with +73% doc completion time
  • Chunk → gate → separate, in that order; and a copied number is not a ported tuning (budget semantics differ per engine)
